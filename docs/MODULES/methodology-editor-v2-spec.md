# ТЗ: редактор методик, этап 2 — шкалы, нормы, доступ к ссылке, статистика

> Статус: **утверждено владельцем 2026-11-07** (этапы 1–5; §4.2 — [решить]). Продолжение
> ADR-037 и `docs/MODULES/methodology-editor-spec.md`. Основание — сравнение с
> конструктором onlinetestpad.com, где центр сейчас проводит тестирование
> («Настроение» = GAD-7, «Оценка общего самочувствия» = HADS, «Работоспособность»,
> «Общение»; около 1700–1800 прохождений каждый). Решения, помеченные **[решить]**,
> принимает владелец до начала соответствующего этапа.

## 1. Задача

Перенести методики центра с onlinetestpad без ручного набора и закрыть
разрыв в возможностях, важный для психодиагностики:

1. Свой набор вариантов ответа у каждого вопроса — в шаблоне xlsx (HADS).
2. Свои уровни и тексты у каждой шкалы; вопрос в нескольких шкалах.
3. Нормы: перевод сырых баллов в стены / T-баллы / проценты.
4. Окно дат и кодовое слово для ссылки кампании.
5. Статистика кампании по вопросам и шкалам.

Вне этапа (учебные функции onlinetestpad, для службы не нужны): соответствия,
пропуски, диктант, слова из букв, сертификат, стилизация, виджет, офлайн-архив,
рейтинг, ограничение по IP/cookie (для анонимной ссылки неприменимо без
сбора идентификаторов устройства — противоречит минимизации ПДн).

## 3. Свой набор вариантов у вопроса в шаблоне xlsx

**Без миграции** — в БД варианты уже принадлежат вопросу (`options.question_id`).

- Новый необязательный лист **«Варианты вопросов»**: `№ вопроса | Порядок | Текст`.
  - Если у вопроса есть строки на этом листе — используются они; иначе общий
    набор с листа «Варианты ответа».
  - Лист «Варианты ответа» становится необязательным, если каждый вопрос
    описан на «Вариантах вопросов».
  - Порядок 1..K без пропусков внутри вопроса; не больше 20 вариантов.
- Лист «Ключ» не меняется: `Вариант` — порядок варианта у этого вопроса.
- **Выгрузка:** если у всех вопросов одинаковые тексты и порядок вариантов —
  как сейчас (общий набор); иначе все варианты — на «Вариантах вопросов».
- **Проверки** с адресом лист/строка/колонка: вопрос без вариантов; дубль
  порядка; ссылка ключа на несуществующий вариант этого вопроса.
- **Тест туда-обратно:** HADS-подобная методика (14 вопросов, разные тексты
  вариантов, обратный ключ, 2 шкалы) — выгрузка → импорт → идентичные вопросы,
  варианты, ключ и правила. ИТО — результат прежний (регрессия).

## 4. Шкалы

### 4.1 Уровни у каждой шкалы

**Без миграции** (JSONB `scoring_rules`), схема остаётся `version: 1`,
поле добавляется необязательным:

```json
"scales": [
  {"code": "A", "label": "Тревога", "main": true,
   "levels": [
     {"code": "norm", "label": "Норма", "min": 0, "max": 7},
     {"code": "subclinical", "label": "Субклинически выраженная", "min": 8, "max": 10},
     {"code": "clinical", "label": "Клинически выраженная", "min": 11, "max": 21}
   ]}
]
```

- Нет `scales[].levels` — берутся общие `levels` (поведение ИТО не меняется).
- Правила для уровней шкалы — те же, что для общих (код, пересечения, ≤ 10);
  `analyze_test` проверяет покрытие диапазона именно этой шкалы.
- Цвет уровня в экране «Результаты» (`tone`) — по положению уровня в списке,
  как сейчас.
- xlsx: на листе «Уровни» новая необязательная колонка **«Шкала»** (пусто —
  общий уровень).
- UI: в «Правилах обработки» у шкалы переключатель «Свои уровни».
- Колонки выгрузки «Уровни» кампании: подпись уровня по своей шкале.

### 4.2 Вопрос в нескольких шкалах **[решить]**

Сейчас `questions.config.scale` — одна шкала, балл — `options.value_score`.

Предлагаемое хранение (без миграции, в существующем JSONB `questions.config`):

```json
{"scale_scores": {"A": {"1": 3, "2": 2, "3": 1, "4": 0}, "D": {"1": 0, "2": 1, "3": 2, "4": 3}}}
```

- Ключ — порядок варианта; нет записи — 0.
- Если `scale_scores` нет — прежнее правило (`config.scale` + `value_score`),
  ИТО и все существующие тесты не трогаются.
- `value_score` для такого вопроса = 0 (общий балл теста не двоится);
  итог теста — сумма/среднее по шкалам как сейчас для многошкальных.
- Затрагивает `scoring.py` (баллы по шкалам), `score_bounds`, анализ,
  `campaign_response_scales`, выгрузку и импорт (лист «Ключ» уже допускает
  несколько строк на вопрос с разными шкалами — снимается проверка «не
  больше одной шкалы»).
- Регрессия: эталон ИТО (`test_campaign_golden_ito.py`) без изменений.
- **[решить]** нужен ли этот пункт сейчас: из четырёх методик центра ни одна
  его не требует (GAD-7 — одна шкала, HADS — вопросы 1–7 и 8–14 в разных
  шкалах). Рекомендация — отложить до первой методики, где он нужен.

## 5. Нормы: перевод сырых баллов

**Решения владельца (2026-11-07):** нормы применяются **только в тестировании
по ссылке** (в каталоге студента пола и возраста нет — новые ПДн не собираем);
механизм закладывается расширяемым.

**Источник для ИТО.** Проверено: книга Собчик Л. Н. (2002) целиком, включая
таблицы и ссылки в тексте (работы 1972–1993 гг. — про ДМО, не про ИТО;
раздел «Методические разработки…» с. 93 в файле отсутствует), ключ `ИТО
(ключ).xls`, бланк, `ИТО Собчик_шкалы_типы.docx`, пример выгрузки. Таблиц
перевода в стены/T-баллы и поправок на пол и возраст в методичке **нет**:
нормой служат сырые баллы 0–9 (0–2 / 3–4 / 5–7 / 8–9), достоверность L, F > 5,
тип — шкала > 7. Всё это уже в `scoring_rules`. ИТО остаётся на сырых баллах,
норм не получает; механизм проверяется на синтетических таблицах.

```json
"scales": [{"code": "A", "...": "...",
  "norms": {
    "kind": "sten",
    "label": "Стены",
    "groups": [
      {"when": [{"field": "gender", "eq": "female"},
                {"field": "age", "min": 17, "max": 25}],
       "table": [{"min": 0, "max": 3, "value": 1}, {"min": 4, "max": 5, "value": 2}]},
      {"when": [], "table": [{"min": 0, "max": 3, "value": 1}]}
    ]}}]
```

- **Расширяемость:**
  - `kind` — открытый перечень (`sten`, `t`, `stanine`, `percentile`, `custom`),
    влияет только на подпись по умолчанию; значение — число из таблицы;
  - условия группы `when` — список условий по полям анкеты кампании
    (`gender` — `eq`; `age` — `min`/`max`; `faculty_code` — `eq`); новое поле
    анкеты добавляется в одном перечне допустимых полей, схема не меняется;
  - группа без условий — запасная.
- Таблица «сырой балл → стандартный балл» (а не формула): так нормы даются в
  методичках, и её легко сверить. Диапазоны таблицы не пересекаются.
- Группа — первая подходящая по порядку. Нет подходящей — стандартный балл не
  считается (пусто), ближайшая не подставляется.
- Пересчёт — при выгрузке и на экране «Результаты» (как уровни), не при
  сохранении ответа: правка норм в черновике новой версии не трогает прежние
  кампании (они на своей версии теста).
- Выгрузка xlsx кампании: колонка «<шкала> (<label>)» рядом с сырым баллом —
  только у шкал с нормами.
- Шаблон методики: лист **«Нормы»**: `Шкала | Пол | Возраст от | Возраст до |
  Сырой от | Сырой до | Значение` (+ лист «Шкалы» — тип и подпись норм).
- Уровни по стандартному баллу (`levels_on: "norm"`) — следующий шаг, после
  появления методики с такими нормами.
- Каталог студента: нормы не применяются и студенту не показываются.

## 6. Окно дат и кодовое слово кампании

**Миграция** `test_campaigns`:
- `opens_at` TIMESTAMPTZ NULL, `closes_at` TIMESTAMPTZ NULL, CHECK `opens_at < closes_at`;
- `access_code_hash` TEXT NULL — bcrypt (как пароли), открытый текст нигде не хранится.

**Поведение публичной ссылки:**
- до `opens_at` — «Тестирование начнётся <дата>», анкета не показывается;
- после `closes_at` — как закрытая кампания (тот же ответ, что сейчас для `closed`);
  статус в БД сам не меняется, «Открыть снова» продлевает/снимает `closes_at`.
- кодовое слово: поле перед анкетой; проверка на сервере в том же запросе
  отправки ответа (нет отдельного «токена допуска»); неверное — 403
  `access_code_invalid`, ответ не сохраняется;
- лимит попыток кода — существующий `app/core/rate_limit.py` (на ссылку + IP,
  например 10 в 10 минут), 429.
- Время проверяется по серверу; на клиенте — только подсказка.

**Кабинет супервизора:** в карточке кампании «Сроки» (даты/время, часовой пояс
сервера — Москва) и «Кодовое слово» (задать / сменить / снять; после
сохранения слово не показывается — супервизор сообщает его студентам сам).

**Аудит** (`_CAMPAIGN_META`, ATOMIC/RAISE под FOR UPDATE кампании):
- `test_campaign_schedule_changed` — даты в metadata не пишутся;
- `test_campaign_access_code_changed` — ни слово, ни хеш в metadata не пишутся.
- Неверный код — без события (анонимный поток, как прочие отказы ADR-036).
- Счётчики REGISTRY и тесты — по чек-листу §7 ТЗ этапа 1.

## 7. Статистика кампании

Новая вкладка **«Статистика»** на экране «Результаты» (тот же доступ и то же
событие `campaign_results_read`; новых событий нет):

- **По дням:** число прохождений по датам.
- **По вопросам:** для каждого вопроса — сколько участников выбрали каждый
  вариант (число и %); для `scale` — распределение значений; `free_text`
  не показывается.
- **По шкалам:** распределение сырых баллов (гистограмма) и доли уровней —
  у основных шкал.
- Фильтры — те же, что на экране «Результаты» (факультет, пол, достоверность,
  тип).
- **Защита от узнавания:** если в выбранной группе меньше 5 участников —
  распределения не показываются («слишком мало участников для статистики»).
  ФИО в этой вкладке нет.
- Выгрузка: лист **«Статистика по вопросам»** в xlsx кампании.
- Расчёт — на сервере (`app/campaigns/analytics.py`), JSON-эндпоинт под
  `/api/supervisor/campaigns/{uuid}/statistics`; графики — общий компонент
  графиков фронтенда (по `docs/UI_COMPONENTS_GUIDE.md`).
