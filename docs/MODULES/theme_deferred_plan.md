## T2. Дочистка хардкода в pages/features

Остаток после этапа 4: **104 hex + 231 raw rgba** только в `pages/` и `features/`
(общие `components/` чистые). Распределение hex: student 35, supervisor 13,
psychologist 11, services 10, auth 10, admin 7, news 6, materials 4 (+features).

Батчи (каждый — свой коммит, свой dark-smoke):

1. **auth + public** (~30 hex): `features/auth/*` (AuthModal, RegisterForm,
   forgot-password), `pages/services/ServiceCard`, `pages/news`, `pages/materials`,
   `features/news/*` (jsx-инлайны NewsCardSmall/FeaturedNews/NewsListItem,
   QuickActions, MaterialCard — перевод SVG на currentColor по образцу Navbar).
2. **student** (~35 hex): Diary (DiaryEntryItem.jsx + .module.css, DiaryPage),
   Calendar (+ SessionPopover, CalendarDayPopup — там inline `var(--…)` уже есть),
   Settings, Chat/AttachmentPreviewLightbox, Tests.
3. **psychologist + supervisor + admin** (~31 hex): PsychologistStudentCardPage,
   SchedulePage, MeetingTypesPage, GroupSessionsPage, BookingPage, admin-модули.

Метод (как в этапе 4):

- замена по роли на существующие токены; `rgba(X, a)` → `rgba(var(--x-rgb), a)`;
  новый токен — только если роль отсутствует (добавлять во все 4+ темы сразу
  и в PAIRS `check-contrast.js`, если это пара текст/фон);
- вести список осознанных исключений (scrim поверх фото, brand-цвета) —
  сейчас: `icons/index.jsx`, `ImageUpload.module.css`;
- приёмка батча: grep hex/rgba по батчу = 0 (кроме исключений), build, dark-smoke.

Приёмка этапа: `grep -rE '#[0-9a-fA-F]{3,8}' --include='*.css' src | grep -v tokens`
— только файлы-исключения; все страницы презентабельны в обеих dark-темах.

## T3. Синхронизация темы с профилем пользователя

Сейчас тема живёт в localStorage (per-device). Цель — переносимость между
устройствами для авторизованных. Endpoint `GET/PATCH /api/auth/profile` уже есть
(`app/auth/routes.py:153`, `ProfileRead`/`ProfileUpdate`).

Backend (0.5 сессии):

- Alembic-миграция: `users.ui_theme_palette VARCHAR(20) NULL`,
  `users.ui_theme_mode VARCHAR(10) NULL` (NULL = «не задано», действует клиент);
- `ProfileRead`/`ProfileUpdate` + service: whitelist-валидация
  (`coffee|nature|classic…` / `light|dark|system`) → 422 при мусоре;
- значения темы — не ПДн-чувствительные, но в audit/логи их всё равно не писать;
- тесты: расширить `tests/integration/test_auth_profile.py`
  (roundtrip, 422 на невалидные, NULL-семантика, PATCH без полей темы не трогает их).

Frontend (0.5 сессии):

- `auth.api.js` — поля темы в profile-вызовах (fetch только в api-слое);
- ThemeContext: приоритет источников — **явный выбор в текущей сессии >
  профиль > localStorage > default(system)**; при логине подтягивать из профиля
  (и записывать в localStorage — анти-FOUC скрипт читает только его);
  при смене темы авторизованным — PATCH soft-fail (ошибка сети не ломает UI);
- гость — как сейчас (localStorage);
- тесты ThemeContext на приоритет источников (мок api).

## T4. Высококонтрастные темы (hc)

Модель: hc — **отдельная пара тем, не палитра×режим** (`hc-light`, `hc-dark`);
при выборе hc выбор палитры неактивен. Это 2 css-файла и минимум UI-правок;
не плодим 4 палитры × hc.

- `tokens/hc-light.css` (surface #FFFFFF, on-surface #000000, primary #1E4A2E,
  outline #1A1A1A, фокус 3px #B45309 + offset 2px) и `tokens/hc-dark.css`
  (surface #0B0D0C, on-surface #FFFFFF, primary #C8E6CF, outline #E5E5E5,
  фокус 3px #FFD54F); все легаси-алиасы замаплены по роли;
- глобальные hc-оверрайды в самих файлах тем: видимая рамка 1–2px на
  интерактивных элементах и карточках (`:root[data-theme^='hc-'] button/a/input…`),
  ссылки подчёркнуты — БЕЗ правки компонентов; предварительный аудит,
  где рамки ломают layout;
- автоопределение: `prefers-contrast: more` при отсутствии сохранённого выбора
  (анти-FOUC скрипт + ThemeContext);
- ThemeToggle: третий пункт контраста или отдельная кнопка — решить на этапе
  (в navbar уже 2 группы; вероятно, компактный дизайн-пересмотр контрола,
  например Select-подобный дропдаун темы вместо сегментов — отдельное обоснование);
- `check-contrast.js`: THEMES += hc-темы, порог **7.0** (AAA) для hc,
  исключений 3.0 в hc быть не должно;
- T3-совместимость: whitelist профиля расширить.

## T5. Режим для слабовидящих (ГОСТ Р 52872-2019)

Отдельный полнофункциональный режим поверх hc-инфраструктуры. Юридически
обязателен для образовательной организации. Разбивка на подэтапы:

**T5.1 Инфраструктура настроек** (~1 сессия)

- `data-a11y="on"` на `<html>` + отдельный контекст `A11ySettingsContext`
  (не смешивать с ThemeContext): размер шрифта 100/150/200%, схема
  (Ч/Б #FFF/#000, Б/Ч #000/#FFF, синяя #9DD1FF/#063462, бежевая #F7F3D6/#4D4B31),
  межбуквенный (0/0.05/0.1em), межстрочный (1.5/2), serif/sans, изображения
  (показывать/скрыть-в-alt-рамку/grayscale), сброс; персистентность localStorage
  (+ поля в профиль по образцу T3);
- масштаб шрифта: перевести `--fs-*` в `variables.css` на
  `calc(clamp(…) * var(--font-scale, 1))` — единственная правка типографики,
  работает во всех темах;
- `tokens/a11y-*.css` — 4 схемы как токен-наборы.

**T5.2 Панель и вход в режим** (~1 сессия)

- Кнопка «Версия для слабовидящих» (иконка глаза + текст, доступна по Tab)
  в Navbar И в topbar CabinetLayout — на каждой странице; выход — «Обычная версия»;
- `A11yPanel` закреплена под шапкой в режиме a11y; все контролы — кнопки с
  `aria-pressed`, панель работает с клавиатуры.

**T5.3 Правила режима** (~1 сессия)

- одноколоночная упрощённая сетка, max-width текста 80ch; отключены декоративные
  элементы/фоновые изображения/анимации (глобальные оверрайды `[data-a11y='on']`);
- ссылки подчёркнуты; статусы записей и результаты тестов дублируются
  текстом/иконкой (не только цветом); прогресс теста — текст «Вопрос N из M»;
- изображения: скрыть → alt-текст в рамке; grayscale → `filter: grayscale(1)`.

**T5.4 Приёмка** (~0.5–1 сессия, частично ручная)

- запись на консультацию и прохождение теста полностью выполнимы с клавиатуры
  при 200% шрифте, ширина 320px CSS, без горизонтального скролла;
- контраст всех 4 схем ≥ 7:1 (добавить схемы в `check-contrast.js`);
- при скрытых изображениях смысл сохраняется через alt;
- ручной прогон обоих кабинетов + чек-лист соответствия ГОСТ в
  `docs/MODULES/theme_gost_checklist.md`.

Ограничение (как в базовом промпте): никаких сторонних виджетов —
только собственная реализация на токенах.

## T6. Палитра Classic (бело-синяя академическая)

По инструкции «Как добавить палитру» из `theme_implementation_plan.md`:

- `tokens/classic-light.css` / `classic-dark.css`: surface #FFFFFF/тёмно-синий,

  ориентир #2B5A9E±), текст — тёмно-серый/графитовый; легаси-алиасы по роли
  (espresso→графит/навы, latte/fog→серо-голубые границы);
- PALETTES, PALETTE_OPTIONS, список в анти-FOUC скрипте, THEMES в contrast-скрипте
  (+ whitelist профиля из T3);
- внимание: 3 палитры в сегмент-контроле ThemeToggle — тесно в navbar;
  вероятно, к этому моменту контрол уже пересмотрен в T4 (дропдаун);
  если T6 идёт раньше — допустим временный третий пункт «Классика»;
- компоненты меняться не должны (критерий архитектуры, как с nature).

## T7. Унаследованные пары контраста 3.0 (дизайн-решение)

Сейчас три пары проходят по порогу 3.0 как «унаследовано из исходного дизайна»:
`--text-light` на фоне (4.27), `--success` на `--success-bg` (3.46),
`--coffee` как акцент-текст (4.45). Доведение до 4.5 = **видимое изменение
светлой темы** (затемнить #8A7260→~#77614F, #5D8A5E→~#4E7850).

- Решение принимает владелец дизайна: (а) принять исключения как задокументированные
  (hc/ГОСТ-режимы покрывают слабовидящих) или (б) затемнить токены;
- при (б): правка только `coffee-light.css` (3 значения + rgb-триплет),
  поднять пороги в PAIRS до 4.5, визуальный смоук светлой темы.
