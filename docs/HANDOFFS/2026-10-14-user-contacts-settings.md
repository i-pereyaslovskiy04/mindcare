## 1. Дефект

В `/student/settings` «Социальные сети», часовой пояс и переключатели
уведомлений жили только в `useState`: на сервер не уходили и пропадали при
обновлении. ФИО и телефон отправлялись одной формой (устаревшее значение одного

обеспечивалась.

## 2. Что сделано

### Backend (`mindcare_api/app/user_contacts/`)

- Таблица `user_contacts` (1:1 с `users`): `contacts_enc` — Fernet `enc:v1:`
  (CHECK), `version` ≥ 1. Контакты не входят в `User`/общие DTO.
- `GET|PUT /api/auth/profile/contacts` (владелец), `GET /api/staff/users/{uuid}/contacts`
  (сотрудник). Все ответы `Cache-Control: no-store, private`.
- PUT: `{version, items}`, у каждого item обязателен клиентский UUID `id`;
  CAS по `version` (несовпадение → 409 `contacts_version_conflict` +
  `current_version`); содержимое равно текущему → no-op (200, `changed:false`,
  без версии/`updated_at`/аудита) — повтор после потерянного ответа безопасен.
- Валидация: типы phone/email/messenger/social/website/other, каталог сервисов
  только в `catalog.py` (расширен: WhatsApp, Viber, MAX, Signal, Skype, OK, YouTube,
  RUTUBE; прежние Telegram, Instagram, LinkedIn, VK, Facebook, X, «Сайт» сохранены);
  лимиты 10 элементов / подпись 80 / значение 500; только http(s)-ссылки;
  дополнительный email — только способ связи (без allowlist доменов).
- `ContactsRoute` санитизирует 422/500: закрытые allowlist'ы `field`/`code`,
  значения не попадают в тело ответа и логи.
- `service.py` без FastAPI/HTTP (AST-тест); права и роль аудита — в `routes*.py`.
- Impersonation закрыт на всех трёх маршрутах (403).

### Frontend

## 3. Матрица доступа к чтению сотрудником

| Кто читает | Цель | Доступ |
|---|---|---|
| Владелец | свои контакты | `GET/PUT /api/auth/profile/contacts` |
| Психолог (`psychologist ∈ roles[]`) | клиент со строгим активным сопровождением (`status='active' AND ended_at IS NULL`); цель активна и не удалена; **в том числе клиент со staff-ролью** | да (грант A, роль аудита `psychologist`) |
| Психолог | завершённое/переданное сопровождение, чужой студент | нет — единый 404 |
| Супервизор (`supervisor ∈ roles[]`) | чистый студент из списка супервизора (активен, не удалён, нет других ролей) | да (грант B, роль аудита `supervisor`) |
| Супервизор | клиент со staff-ролью | только если он его назначенный психолог (грант A); иначе 404 |
| `admin` сам по себе | кто угодно | нет |
| Любой в режиме impersonation | — | 403 |

Порядок: грант A, затем B. Заголовок `X-Active-Role` не используется. В ответ
сотруднику входит `primary_phone` (`users.phone`) — **новое раскрытие**.

Подписи владельцу согласованы с матрицей: чистому студенту — «психологу и
супервизору», владельцу со staff-ролью — «назначенному вам психологу при
действующем сопровождении».

## 5а. Corrective pass (2026-10-15): три замечания по ревью

Новых бизнес-операций, событий аудита и миграций нет; REGISTRY остаётся 123,
минимизация аудита не ослаблена.

1. **`tel:` для форматированного телефона.** Основной телефон хранится в виде
   `+7 (949) 123-45-67` (результат `formatPhoneInput`), а `contactHref` принимал
   только `+цифры` — ссылки не получалось. Теперь `lib/href.js::telDigits`
   принимает необязательный «+», цифры и разделители (пробел, скобки, дефис,
   точка), 7–15 цифр, и отдаёт `+цифры`; отображаемый текст не меняется. Любая
   другая строка (буквы, `;`, `tel:`/`javascript:`, добавочный, слишком
   короткий/длинный номер) ссылкой не становится и показывается текстом.
   Тесты: `href.test.js` (нормализация, 10 негативных строк, цепочка
   `formatPhoneInput → contactHref`) и `ContactsReadOnly.test.jsx` (основной
   телефон сотрудника: `formatPhoneInput` → текст прежний → `tel:+79491234567`;
   нетелефонная строка без ссылки; форматированный дополнительный телефон).
2. **Фокус на настоящем Select.** Shared `components/UI/Select` аддитивно
   получил `id` (без него генерируется), `aria-invalid` и `aria-describedby`
   на id сообщения об ошибке (`<id>-error`); остальные потребители не затронуты
   (без `error` новых aria-атрибутов нет). `aria-invalid` на кнопке-селекте
   правило `jsx-a11y/role-supports-aria-props` считает неподдерживаемым
   (ARIA 1.2) — точечный `eslint-disable` с обоснованием. `ContactsEditor`
   передаёт Select'ам `id` по схеме `fieldDomId(prefix, rowId, 'type'|'service')`,
   поэтому `focusTarget` теперь попадает на контрол, а не на строку. Тесты:
   новый `Select.test.jsx` (id, генерация, связь ошибки, прежнее поведение,
   выбор варианта) и в `ContactsEditor.test.jsx` сквозной сценарий с реальным
   `useMyContacts`: мессенджер без сервиса → «Сохранить контакты» → фокус на
   «Сервис», `aria-invalid`, описание «Выберите сервис».
3. **Стабильность `test_data_change_values_are_never_returned`.** Тест искал
   подстроки `"30"`/`"60"` во всём сериализованном элементе и падал на дате с
   «30» и на UUID. Теперь контрольные значения — уникальные маркеры (две строки
   и два «длинных» числа), проверяются точно по листьям через `_leaf_values`, а
   также по сырому тексту ответа (уникальные маркеры ложно не срабатывают);
   строгие проверки сохранены: ответ 200, `changed_fields`, отсутствие ключей
   `old_values`/`new_values`. Production-код просмотра аудита не менялся.

## 5б. Доработка интерфейса (2026-10-15): вкладки и форма контактов

Только клиентская часть. Backend, API, схема БД, права доступа, чтения данных и
события аудита не менялись (REGISTRY 123, CHANGE_REGISTRY, failure codes — как были).

**Вкладки настроек.** `Tabs` получил prop `indicator` (`'underline'` по умолчанию,
`'fill'` — без подчёркивания); `SettingsPage` использует `fill`, `AuditTabs` и
остальные потребители — прежний вид. Выбранная вкладка: заливка `--primary` +
жирное начертание; в режиме для слабовидящих (где все `button` принудительно
получают фон схемы и рамку 2px) — инверсия и внутренняя рамка (`inset box-shadow`,
размеры и соседние элементы не сдвигаются; приём как в `A11yPanel`). `aria-selected`,
стрелки/Home/End и видимый фокус не менялись; подчёркивание ссылок не затронуто.

**Форма «Дополнительные контакты».** Обычный контакт — два поля:

| Способ связи (из backend-каталога) | `type` / `service` | Значение: подпись · режим ввода | `label` в payload |
|---|---|---|---|
| Телефон | `phone` / — | «Номер телефона» · `tel` | `null`* |
| Email | `email` / — | «Email» · `email` | `null`* |
| Telegram, WhatsApp, Viber, MAX, Signal, Skype | `messenger` / код сервиса | «Имя пользователя, номер или ссылка» | `null`* |
| VK, Одноклассники, Instagram, Facebook, LinkedIn, X, YouTube, RUTUBE | `social` / код сервиса | «Имя пользователя или ссылка» | `null`* |
| Сайт | `website` / — | «Адрес сайта» · `url` | `null`* |
| Другой мессенджер | `messenger` / `other` | «Контакт или ссылка» + **«Название»** | название |
| Другая соцсеть | `social` / `other` | «Контакт или ссылка» + **«Название»** | название |
| Другое | `other` / — | «Контакт» + **«Название»** | название |

\* у нового контакта; у прежнего контакта сохранённый `label` остаётся в данных и
уходит в payload без изменений (поле скрыто, значение не стирается).

- Варианты строит `features/contacts/lib/methods.js::buildMethods` только из
  `catalog` ответа API (копии списка сервисов нет; новый сервис каталога
  появляется без правки клиента). Ключ варианта — `type` или `type:service`
  (`messenger:other` ≠ `social:other`), преобразование в `type`/`service` и обратно
  однозначно; сохранённый контакт вне каталога показывается кодами и не ломает форму.
- «Название» — обязательное поле только у «Другой …» (сервер: `label_required`), это
  не возвращённая «Подпись». Поля «Подпись (необязательно)» и подсказки про
  «рабочий» больше нет.
- `applyMethod` (`lib/draft.js`): смена способа задаёт `type` и `service` вместе
  (прежний `service` не остаётся); название, введённое в этой сессии, на обычный
  способ не переносится, **сохранённая подпись не стирается никогда**.
- Проверка согласована с сервером: «Название» проверяется на клиенте только когда
  поле видно; значения/форматы без изменений (ограничений отдельных сервисов,
  которых нет в контракте, не вводилось); найдено и исправлено одно расхождение —
  дубль телефона в разной записи (`+7 (949)…` и `8949…`) клиент теперь сводит к
  тому же ключу, что `normalize_phone` на сервере; ошибки `type`/`service` показываются
  у селектора «Способ связи» («Выберите способ связи»).
- **Ошибка сервера по скрытой подписи** (теоретически — например, при изменении лимита):
  поля на экране нет, поэтому у контакта показывается сообщение с прежней подписью и
  явная кнопка **«Удалить прежнюю подпись»** (фокус переходит на неё). Автоматически
  ничего не стирается; после действия повторное сохранение уходит с `label:null`.
- Раскладка: заголовок контакта «Контакт N» + кнопка удаления справа (устойчивое
  положение, `aria-label="Удалить контакт N"`); широко — «Способ связи» | значение,
  «Название» — второй строкой на всю ширину; ≤560px — поля друг под другом. Колонки
  гибкие (`minmax(0, …)`), длинные значения и ошибки переносятся.
- Единый вид полей: `Select` и `TextField` получили аддитивный prop
  `appearance="field"` (подписи, рамка, фон, фокус-кольцо, ошибка, общая коробка:
  border-box, рамка 1px, padding 9px, `line-height` 1.4, `min-height` 40px вместо
  фиксированной высоты — при увеличенном шрифте контролы растут, а не обрезают);
  по умолчанию вид прежний. `Select` дополнительно получил `id`, `aria-invalid` и
  `aria-describedby` на сообщение об ошибке — фокус при ошибке попадает на реальный
  контрол. Вариант типа `other` остаётся с подписью «Другое» из каталога.

Сохраняется без изменений: UUID контактов, загрузка и серверное сохранение (CAS по
`version`, no-op при равном содержимом), черновики при смене вкладок и ошибке,
