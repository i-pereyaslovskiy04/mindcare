# Audit Rules

Правила проведения любых аудитов в проекте MindCare.

---

## Перед аудитом прочитать

Перед началом любого аудита убедиться, что актуальный контекст проекта учтён:

- `CLAUDE.md` — основной проектный контекст, архитектура, соглашения, список исключений.
- `docs/UI_COMPONENTS_GUIDE.md` — правила использования shared UI-компонентов.
- `docs/UI_TECH_DEBT.md` — реестр осознанных исключений (что уже не мигрировать без решения).
- `docs/FRONTEND_CHECKLIST.md` — чеклист качества для frontend-задач.

---

## Режим

Любой аудит выполняется только в режиме **READ-ONLY**.

Обязательные строки в промпте на аудит:

```text
Режим READ-ONLY.

Не менять код.
Не создавать файлы.
Не редактировать JSX/CSS/Python.
Не удалять стили.
Не делать рефакторинг.
Не запускать миграцию.
Только анализ и финальный отчёт.
```

---

## Что аудит может делать

- Искать файлы через Glob, Grep, Read.
- Классифицировать компоненты по типам (badge, tag, chip, button, etc.).
- Описывать текущее состояние стилей.
- Выявлять дублирование и расхождения.
- Определять риски (accessibility, визуальные, tech debt).
- Предлагать план миграции.
- Предлагать API (props, variants, tones) будущего компонента.
- Давать рекомендации.
- Формировать список файлов для будущей миграции.

## Что аудит не может делать

- Менять JSX.
- Менять CSS.
- Создавать компоненты или файлы.
- Удалять классы или стили.
- Запускать миграцию.
- Исправлять найденные проблемы без отдельного разрешения пользователя.
- Коммитить или пушить.

---

## Аудит и миграция — разные этапы

```
1. Аудит      — только READ-ONLY анализ. Промпт: "Аудит X. READ-ONLY."
2. Миграция   — изменение кода только по отдельному промпту.
3. Отчёт      — build, grep-верификация, visual risks, accessibility risks.
```

Нельзя совмещать аудит и миграцию в одном промпте, если это не заявлено явно.

---

## Структура финального отчёта аудита

```md
## Финальный отчёт

1. Найдено N элементов типа X в M файлах.
2. Классификация: [таблица или список].
3. Рекомендуемые группы для миграции.
4. Предлагаемый API компонента (props, variants).
5. Риски (accessibility, визуальные, layout-зависимости).
6. Список файлов НЕ рекомендованных к автоматической миграции (с причиной).
7. Код не менялся.
```

## Виды аудитов в проекте

| Тип аудита | Цель | Примеры |
|---|---|---|
| Badge/status audit | Найти все статусные плашки | admin tables, task cards |
| Tag/chip audit | Найти все display-only теги | materials, news, articles |
| Button audit | Найти feature-specific кнопки | card buttons, nav controls |
| Accessibility audit | Найти a11y нарушения | aria, focus, semantic HTML |
| CSS dead code audit | Найти неиспользуемые классы | после миграции |
| API audit | Найти дублирование вызовов | api/*.api.js |

---

## Правила именования аудит-отчётов

Если аудит сохраняется в docs/:

```
docs/audits/AUDIT_<DOMAIN>_<YYYYMMDD>.md
```

Пример: `docs/audits/AUDIT_BADGE_20260601.md`

Аудиты, которые завершились миграцией, не удалять — они фиксируют историю решений.
