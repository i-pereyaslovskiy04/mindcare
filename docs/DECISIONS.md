## Frontend

### ADR-001 — Единый `errors` со строками в формах

**Дата:** 2026-05-20

**Контекст:** В проекте сложились два паттерна обработки ошибок форм:
- `LoginForm`: булевы `errors` + отдельный `apiError` (строка)
- `useForgotPassword`: единый `errors` с строками-сообщениями

При создании `useUserForm` нужно было выбрать один стандарт.

**Решение:** Единый объект `errors` со строками. Клиентские ошибки полей — по ключу поля (`errors.email`), серверные / общие — по ключу `errors._form`.

**Почему:** Строки — это данные, не JSX. Hook возвращает готовое сообщение, компонент просто рендерит `{errors.email}`. Два отдельных состояния (`errors` + `apiError`) — лишняя сложность в hook-е и компоненте.

**Отброшено:** Булевы `errors` + `apiError` — сообщения захардкожены в JSX, не переиспользуются, неудобны в hook-ах.

**Зафиксировано в:** `ARCHITECTURE.md §10 — Error handling в формах`
**Технический долг:** `LoginForm` использует старый паттерн → `BACKLOG.md §🟢`

### ADR-002 — `onSuccess` как параметр hook-а, а не Promise

**Дата:** 2026-05-20

**Контекст:** `useUserForm` должен уведомить вызывающий компонент об успешном завершении операции (создание / обновление пользователя). Два варианта:
- A: `onSuccess` передаётся в hook как параметр, hook вызывает его сам
- B: `handleSubmit` возвращает Promise, компонент сам `.then()` вызывает нужные действия

**Решение:** Вариант A — `onSuccess` как параметр `useUserForm({ mode, uuid, onSuccess })`.

**Почему:** Hook инкапсулирует весь цикл запроса включая обработку ошибок. Компонент только рендерит — не обрабатывает Promise. Вариант B переносит логику обработки ошибок в компонент, что дублирует ответственность.

**Отброшено:** Promise из `handleSubmit` — модалке пришлось бы самой писать `.catch()` и управлять состоянием ошибки, которое уже живёт в hook-е.

### ADR-003 — Два флага: `loading` и `submitting`

**Дата:** 2026-05-20

**Контекст:** В edit-mode `useUserForm` выполняет два разных асинхронных процесса:
1. Начальная загрузка данных пользователя (`getUser`)
2. Отправка изменений (`updateUser`)

**Решение:** Два отдельных флага. `loading` — начальная загрузка (показывает скелетон формы). `submitting` — отправка (блокирует кнопку Submit).

**Почему:** Один флаг `loading` не позволяет различить эти состояния в UI. При загрузке нужно показать скелетон всей формы, при отправке — только спиннер на кнопке.

**Отброшено:** Один `loading` — невозможно показать разный UI для двух разных фаз.

### ADR-004 — `updateUser` отправляет все поля, не только изменённые

**Дата:** 2026-05-20

**Контекст:** PATCH `/api/admin/users/{uuid}` поддерживает partial update на бэке (все поля необязательные). Варианты:
- A: Отправлять только изменённые поля (diff между начальными и текущими values)
- B: Отправлять весь объект `values` целиком

**Решение:** Вариант B — весь объект.

**Почему:** Diff между начальными и текущими значениями требует хранения начального снэпшота и усложняет hook без реальной выгоды. Бэк корректно обрабатывает полный объект. Риск «затереть поле пустым значением» закрывается валидацией на фронте.

**Отброшено:** Diff-подход — излишняя сложность для задачи этого масштаба.

### ADR-005 — `apiFetch` обрабатывает `204 No Content`

**Дата:** 2026-05-20

**Контекст:** `DELETE /api/admin/users/{uuid}` возвращает `204 No Content`. `apiFetch` всегда вызывал `res.json()`, что бросает `SyntaxError` на пустом теле — даже при успехе.

**Решение:** В `client.js` добавлена проверка перед `res.json()`:
```js
if (res.status === 204) return null;
```

**Почему:** `client.js` отвечает за транспорт — правильное место для обработки HTTP-статусов. Все будущие DELETE-эндпоинты получают корректное поведение автоматически.

**Отброшено:** Перехват `SyntaxError` в `deleteUser` — хак, который маскирует реальные ошибки парсинга JSON в других ответах.

## Backend

### ADR-006 — Формат аудит-события для admin-операций: UUID в строке события

**Дата:** 2026-05-21

**Контекст:** `log_auth_event` не имеет поля `target_user_id`. При логировании admin-операций (create/update/delete пользователя) нужно фиксировать не только «кто сделал», но и «над кем». Без этого нельзя ответить на вопрос «когда и кем был изменён конкретный пользователь» — нарушение требований ФЗ-152 к прослеживаемости.

**Решение:** UUID цели закодирован в строке события:
```python
event=f"admin_create_user:{user['uuid']}"
event=f"admin_update_user:{uuid}"
event=f"admin_delete_user:{uuid}"
```

**Почему:** Минимальное изменение без миграции БД. `auth_log` уже партиционирован и менять его схему в рамках этой задачи нецелесообразно.

**Отброшено:** Добавить поле `target_user_id` в `AuthLog` — правильное решение, но требует Alembic-миграции. Отложено в бэклог.

**Зафиксировано в:** `BACKLOG.md §🔵` — «Аудит-лог admin-операций: добавить target_user_id»

### ADR-007 — `_ROLE_PRIORITY` для детерминированного выбора роли

**Дата:** 2026-05-21

**Контекст:** `find_users` и `get_user_by_uuid` использовали `outerjoin` к таблице ролей без `DISTINCT`. При нескольких ролях у одного пользователя (M:N схема `user_roles`) запрос возвращал дублирующиеся строки — пагинация и `total` ломались.

**Решение:** Заменить JOIN на коррелированный подзапрос с явным приоритетом ролей:
```python
_ROLE_PRIORITY = sa_case(
    (Role.name == "admin",        1),
    (Role.name == "supervisor",   2),
    (Role.name == "psychologist", 3),
    (Role.name == "student",      4),
    else_=5,
)
```
Подзапрос с `ORDER BY _ROLE_PRIORITY LIMIT 1` гарантирует одну строку на пользователя и детерминированный выбор самой привилегированной роли.

**Почему:** Одна константа на уровне модуля инкапсулирует всю логику приоритетов. При добавлении новой роли или изменении приоритетов меняется только `_ROLE_PRIORITY` — остальной код не трогается.

**Отброшено:** `.distinct(User.id)` — PostgreSQL-специфичный синтаксис, требует совместимого `ORDER BY`. Коррелированный подзапрос чище и переносимее.
