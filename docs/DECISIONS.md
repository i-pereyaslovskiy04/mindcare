## Frontend

### ADR-001 — Единый `errors` со строками в формах

**Дата:** 2026-05-20

**Контекст:** В проекте сложились два паттерна обработки ошибок форм:
- `LoginForm`: булевы `errors` + отдельный `apiError` (строка)
- `useForgotPassword`: единый `errors` с строками-сообщениями

При создании `useUserForm` нужно было выбрать один стандарт.

**Решение:** Единый объект `errors` со строками. Клиентские ошибки полей — по ключу поля (`errors.email`), серверные / общие — по ключу `errors._form`.

**Почему:** Строки — это данные, не JSX. Hook возвращает готовое сообщение, компонент просто рендерит `{errors.email}`. Два отдельных состояния (`errors` + `apiError`) — лишняя сложность в hook-е и компоненте.

**Отброшено:** Булевы `errors` + `apiError` — сообщения захардкожены в JSX, не переиспользуются, неудобны в hook-ах.

**Зафиксировано в:** `ARCHITECTURE.md §10 — Error handling в формах`
**Технический долг:** `LoginForm` использует старый паттерн → `BACKLOG.md §🟢`

### ADR-002 — `onSuccess` как параметр hook-а, а не Promise

**Дата:** 2026-05-20

**Контекст:** `useUserForm` должен уведомить вызывающий компонент об успешном завершении операции (создание / обновление пользователя). Два варианта:
- A: `onSuccess` передаётся в hook как параметр, hook вызывает его сам
- B: `handleSubmit` возвращает Promise, компонент сам `.then()` вызывает нужные действия

**Решение:** Вариант A — `onSuccess` как параметр `useUserForm({ mode, uuid, onSuccess })`.

**Почему:** Hook инкапсулирует весь цикл запроса включая обработку ошибок. Компонент только рендерит — не обрабатывает Promise. Вариант B переносит логику обработки ошибок в компонент, что дублирует ответственность.

**Отброшено:** Promise из `handleSubmit` — модалке пришлось бы самой писать `.catch()` и управлять состоянием ошибки, которое уже живёт в hook-е.

### ADR-003 — Два флага: `loading` и `submitting`

**Дата:** 2026-05-20

**Контекст:** В edit-mode `useUserForm` выполняет два разных асинхронных процесса:
1. Начальная загрузка данных пользователя (`getUser`)
2. Отправка изменений (`updateUser`)

**Решение:** Два отдельных флага. `loading` — начальная загрузка (показывает скелетон формы). `submitting` — отправка (блокирует кнопку Submit).

**Почему:** Один флаг `loading` не позволяет различить эти состояния в UI. При загрузке нужно показать скелетон всей формы, при отправке — только спиннер на кнопке.

**Отброшено:** Один `loading` — невозможно показать разный UI для двух разных фаз.

### ADR-004 — `updateUser` отправляет все поля, не только изменённые

**Дата:** 2026-05-20

**Контекст:** PATCH `/api/admin/users/{uuid}` поддерживает partial update на бэке (все поля необязательные). Варианты:
- A: Отправлять только изменённые поля (diff между начальными и текущими values)
- B: Отправлять весь объект `values` целиком

**Решение:** Вариант B — весь объект.

**Почему:** Diff между начальными и текущими значениями требует хранения начального снэпшота и усложняет hook без реальной выгоды. Бэк корректно обрабатывает полный объект. Риск «затереть поле пустым значением» закрывается валидацией на фронте.

**Отброшено:** Diff-подход — излишняя сложность для задачи этого масштаба.

### ADR-005 — `apiFetch` обрабатывает `204 No Content`

**Дата:** 2026-05-20

**Контекст:** `DELETE /api/admin/users/{uuid}` возвращает `204 No Content`. `apiFetch` всегда вызывал `res.json()`, что бросает `SyntaxError` на пустом теле — даже при успехе.

**Решение:** В `client.js` добавлена проверка перед `res.json()`:
```js
if (res.status === 204) return null;
```

**Почему:** `client.js` отвечает за транспорт — правильное место для обработки HTTP-статусов. Все будущие DELETE-эндпоинты получают корректное поведение автоматически.

**Отброшено:** Перехват `SyntaxError` в `deleteUser` — хак, который маскирует реальные ошибки парсинга JSON в других ответах.

### ADR-006 — Формат аудит-события для admin-операций: UUID в строке события

> ⚠️ **SUPERSEDED** (Stage 3 / Stage 4B-4; окончательно — ADR-021).
> Описанный ниже формат БОЛЬШЕ НЕ ЯВЛЯЕТСЯ текущим решением и не должен
> применяться в новом коде. Запись сохранена как исторический контекст.
>
> **Актуальная каноника (actor/target-модель):**
> - admin CRUD пишется в **`audit_log`**, а не в `auth_log`;
> - `audit_log.user_id` / `user_role` — **actor** (кто совершил действие);
> - `audit_log.entity_type` / `entity_id` — **target** (над чем);
> - UUID цели **НЕ кодируется** в `event_type`: имена событий — стабильный
>   snake_case из закрытого registry (`admin_user_created`,
>   `admin_user_updated`, `admin_user_deleted`, `admin_role_add`, …);
> - поле `target_user_id` в `auth_log` **не вводится** и не требуется —
>   `auth_log` покрывает только аутентификацию и жизненный цикл сессии.
>
> Field-level дополнение («какие именно поля изменились») живёт в
> `data_change_log` — см. **ADR-021**.
>
> **Историческая правка формулировки:** исходный текст ниже утверждал, что
> отсутствие `target_user_id` было «нарушением требований ФЗ-152 к
> прослеживаемости». Это утверждение не подкреплено и не воспроизводится в
> текущей документации: прослеживаемость трактуется как инженерная задача, а
> оценка соответствия законодательству остаётся за DPO/ответственным лицом.

**Дата:** 2026-05-21

**Контекст (исторический):** `log_auth_event` не имел поля `target_user_id`. При
логировании admin-операций (create/update/delete пользователя) требовалось
фиксировать не только «кто сделал», но и «над кем» — иначе нельзя было ответить
на вопрос «когда и кем был изменён конкретный пользователь».

**Решение (историческое, отменено):** UUID цели закодирован в строке события:
```python
event=f"admin_create_user:{user['uuid']}"
event=f"admin_update_user:{uuid}"
event=f"admin_delete_user:{uuid}"
```

**Почему тогда:** Минимальное изменение без миграции БД. `auth_log` уже
партиционирован, и менять его схему в рамках той задачи было нецелесообразно.

**Отброшено тогда:** Добавить поле `target_user_id` в `AuthLog`. Итоговое
решение оказалось третьим: перенести admin CRUD в `audit_log`, где actor и
target уже разделены структурно, и не расширять `auth_log` вовсе.

### ADR-007 — `_ROLE_PRIORITY` для детерминированного выбора роли

**Дата:** 2026-05-21

**Контекст:** `find_users` и `get_user_by_uuid` использовали `outerjoin` к таблице ролей без `DISTINCT`. При нескольких ролях у одного пользователя (M:N схема `user_roles`) запрос возвращал дублирующиеся строки — пагинация и `total` ломались.

**Решение:** Заменить JOIN на коррелированный подзапрос с явным приоритетом ролей:
```python
_ROLE_PRIORITY = sa_case(
    (Role.name == "admin",        1),
    (Role.name == "supervisor",   2),
    (Role.name == "psychologist", 3),
    (Role.name == "student",      4),
    else_=5,
)
```
Подзапрос с `ORDER BY _ROLE_PRIORITY LIMIT 1` гарантирует одну строку на пользователя и детерминированный выбор самой привилегированной роли.

**Почему:** Одна константа на уровне модуля инкапсулирует всю логику приоритетов. При добавлении новой роли или изменении приоритетов меняется только `_ROLE_PRIORITY` — остальной код не трогается.

**Отброшено:** `.distinct(User.id)` — PostgreSQL-специфичный синтаксис, требует совместимого `ORDER BY`. Коррелированный подзапрос чище и переносимее.

### ADR-008 — `GET /api/admin/users/{uuid}` возвращает 404 для удалённых пользователей

**Дата:** 2026-05-28

**Контекст:** `GET /api/admin/users` с флагом `include_deleted=true` возвращает удалённых пользователей в списке. При этом `GET /api/admin/users/{uuid}` и `get_user_by_uuid` в storage всегда фильтруют `deleted_at IS NULL` и возвращают 404 для удалённых. Это создаёт асимметрию: объект виден в списке, но недоступен по прямому URL.

**Решение:** Оставить 404 для удалённых в одиночном GET. Не добавлять `include_deleted` в `get_user_by_uuid`.

**Почему:**
- Edit-модалка использует данные из строки таблицы (`userInfo` prop), а не делает отдельный GET-запрос — асимметрия не мешает на практике.
- Удалённый пользователь не должен быть редактируемым через прямой URL — защита от случайных операций над deleted-записями.
- Добавление `include_deleted` в одиночный GET потребует аналогичного флага в PATCH/DELETE и усложнит логику «что можно делать с удалённым пользователем».

**Отброшено:** Пробрасывать `include_deleted` в `get_user_by_uuid` — расширяет поверхность для операций над soft-deleted записями без очевидной необходимости.

**Ограничение:** Если в будущем появится «просмотр профиля удалённого» как отдельный экран (read-only), потребуется отдельный эндпоинт, а не модификация текущего.

### ADR-009 — Теги без slug: UUID как внешний идентификатор

**Дата:** 2026-05-28

**Контекст:** При проектировании таблицы `tags` стоял вопрос — нужен ли `slug` (URL-дружественная строка, например `trevoga` из «Тревога»). Slug обычно используется когда теги появляются в публичных URL (`/articles?tag=trevoga`).

**Решение:** Без slug. Внешний идентификатор — `uuid`, как и у пользователей.

**Почему:** Публичные URL по тегам не запланированы в MVP. Для фильтрации контента достаточно `?tag_uuid=...` или `?tag=Тревога`. Slug потребовал бы транслитерации кириллицы (внешняя библиотека или самописная функция) и ещё одного уникального индекса без практической пользы на текущем этапе.

**Отброшено:** Slug через транслитерацию — усложнение без выгоды. Если понадобятся SEO-URL по тегам — добавить `slug` через миграцию, автогенерировать из существующих `name`.

### ADR-010 — Три junction-таблицы вместо полиморфной для тегов

**Дата:** 2026-05-28

**Контекст:** Теги применяются к трём сущностям: `articles`, `news`, `tests`. Два варианта схемы:
- A: Три отдельные таблицы `article_tags`, `news_tags`, `test_tags` — FK на конкретную таблицу
- B: Одна полиморфная `content_tags (tag_id, entity_type, entity_id)` — без FK

**Решение:** Вариант A — три отдельные таблицы.

**Почему:** FK-целостность критична — БД гарантирует что `article_id` существует в `articles`. В полиморфном варианте `entity_id` — просто число без FK, можно привязать тег к несуществующей записи. Три таблицы соответствуют уже принятому стилю проекта (`article_categories`, `test_categories`). Типов контента три и они стабильны.

**Отброшено:** Полиморфная таблица — нет FK-целостности, сложнее запросы (`WHERE entity_type = 'article'`). Оправдана при 10+ типах контента или частом добавлении новых.

### ADR-011 — Нормализация имени тега: capitalize first, lowercase rest

**Дата:** 2026-05-28

**Контекст:** Теги вводит администратор вручную. Без нормализации «тревога», «Тревога», «ТРЕВОГА» стали бы разными тегами несмотря на уникальный индекс `lower(name)`.

**Решение:** Нормализация в `service._normalize()`:
```python
name = name.strip()
return name[0].upper() + name[1:].lower()
```
Дополнительно — уникальный индекс `lower(name)` в БД как защитный слой от race condition.

**Почему:** Единообразное отображение: «Управление тревогой» выглядит лучше чем «управление тревогой» или «УПРАВЛЕНИЕ ТРЕВОГОЙ». Нормализация в service (не в storage и не в компоненте) — бизнес-правило живёт в правильном слое.

**Отброшено:** `str.capitalize()` — в Python lowercase всё после первого символа, что ломает аббревиатуры и многословные теги с заглавными буквами в середине. Явная операция `name[0].upper() + name[1:].lower()` предсказуемее.

### ADR-012 — Категории в MVP плоские, без `parent_id` в Admin CRUD

**Дата:** 2026-06-05

**Контекст:** Таблица `categories` исторически поддерживает иерархию через `parent_id`, но текущий MVP использует категории только как типы материалов для фильтрации и выбора в статьях. Иерархическое дерево усложняет UI, валидацию и поведение soft delete без явной продуктовой пользы на текущем этапе.

**Решение:** В Admin Categories CRUD категории считаются плоским списком. `parent_id` остаётся в БД и ORM-модели, но не принимается в create/update схемах нового CRUD, не отображается в UI и при создании выставляется как `None`.

**Почему:** Пользовательская задача сейчас — управлять типами материалов, а не деревом разделов. Плоский список проще для админа и меньше создаёт скрытых состояний вроде дочерних категорий у скрытого родителя.

**Отброшено:** Реализовать выбор родителя и tree-логику сразу — преждевременное усложнение. Если иерархия понадобится позже, её нужно вернуть отдельной задачей с отдельным UX и правилами удаления.

### ADR-013 — `id` как внешний идентификатор Admin Categories API

**Дата:** 2026-06-05

**Контекст:** В отличие от `users`, `news`, `articles` и `tags`, модель `Category` не имеет UUID. При этом `articles` уже используют категории через `category_ids` и M:N таблицу `article_categories`.

**Решение:** Admin Categories API использует INT `id` в URL: `/api/admin/categories/{id}`.

**Почему:** Это соответствует существующей модели и уже принятому контракту материалов. Добавление UUID потребовало бы миграции и изменения схемы без необходимости для MVP.

**Отброшено:** Добавить `uuid` в `categories` ради единообразия с другими admin CRUD — правильнее для долгосрочной консистентности, но сейчас это миграция без практической выгоды.

### ADR-015 — Supervisor не входит в admin panel

**Дата:** 2026-06-10

**Контекст:** Роль `supervisor` присутствует в системе и имеет отдельный кабинет `/supervisor`. В `AdminLayout.jsx` исторически существовал тернарный оператор `user?.role === 'supervisor' ? 'Супервизор' : 'Администратор'`, хотя `/admin/*` route guard разрешает доступ только роли `admin`. Supervisor никогда не мог попасть в AdminLayout, ветка была мёртвым кодом.

**Текущая модель доступа:**

| Роль | Кабинет | Что может делать |
|------|---------|-----------------|
| `admin` | `/admin/*` | Пользователи, платформенный контент, новости, материалы, категории, темы |
| `supervisor` | `/supervisor/*` | Операционное управление службой; moderation-функции только отдельными supervisor flows |
| `psychologist` | `/psychologist/*` | Свои студенты, сессии, чаты, черновики материалов/тестов |
| `student` | `/student/*` | Личный кабинет |

**Решение:** Supervisor не является пользователем admin panel и не должен иметь доступ к `/admin/*`. Мёртвая ветка удалена. Политика зафиксирована явно. Если supervisor участвует в модерации контента/тестов, это реализуется отдельными `/supervisor/*` flows и отдельными backend-проверками, а не доступом в `/admin/*`.

**Почему:** `/admin/*` остаётся техническим и платформенным контуром. Совмещение admin panel и supervisor-контуров расширило бы доступ ко всем admin endpoints, хотя supervisor нужны только операционные и явно разрешённые moderation-сценарии.

**Отброшено:** Добавить supervisor в `/admin` — расширение полномочий без продуктовой необходимости. Если понадобится новая moderation-функция supervisor, это отдельная задача в `/supervisor/*` с явным изменением backend `require_role`/scope-checks и frontend routes.

### ADR-014 — Soft delete категорий через `is_active=False`

**Дата:** 2026-06-05

**Контекст:** Категории используются материалами через `article_categories`, а также могут использоваться другими контентными модулями. Физическое удаление категории с каскадом удалило бы связи и могло изменить исторические материалы.

**Решение:** `DELETE /api/admin/categories/{id}` не удаляет строку физически. Он выставляет `is_active=False`; связи `article_categories` не трогаются.

**Почему:** Существующие материалы сохраняют привязку, а скрытая категория перестаёт предлагаться для новых материалов через списки активных категорий. Это безопаснее для контента и соответствует смыслу поля `is_active`.

**Отброшено:** Физическое удаление через `db.delete(category)` — слишком разрушительно для таксономии контента. Также отброшено каскадное очищение `article_categories`, потому что оно меняет уже созданные материалы.

### ADR-016 — Разделение ролей в консультационном, контентном и тестовом контурах

**Дата:** 2026-06-08

**Контекст:** В MindCare есть роли `admin`, `supervisor`, `psychologist` и `student`. Модули записей на консультации, чатов и результатов тестов работают с чувствительными психологическими данными. При этом новости, материалы и тесты требуют редакционного управления и модерации.

**Решение:** `admin` отвечает за техническое и контентное администрирование платформы: пользователи, роли, темы, типы материалов, новости, материалы, тесты и публикация контента.
`supervisor` отвечает за операционное управление психологической службой: записи на приём, назначение психологов, чаты, нагрузка, спорные случаи, результаты тестов и модерация контента.
`psychologist` работает только со своими студентами, своими чатами и своими записями. Психолог может создавать материалы и тесты, но не может публиковать их напрямую. Публикация требует модерации `admin` или `supervisor`.
`student` создаёт записи на приём, работает со своими чатами и проходит опубликованные тесты.

**Модерация:** Для материалов и тестов используется общий цикл `draft -> in_review -> published`; дополнительно допустим статус `needs_changes`. Психолог создаёт материалы и тесты как черновики и отправляет их на проверку. Публиковать или возвращать на доработку могут только `admin` и `supervisor`. Публично виден только статус `published`.

**Доступ к результатам тестов:** `supervisor` может видеть результаты тестов студентов в рамках операционного управления психологической службой. `psychologist` видит результаты только тех студентов, с которыми есть активная или прошлая назначенная консультация. `admin` не получает регулярный доступ к результатам тестов по умолчанию.

**Почему:** Такое разделение ограничивает доступ к чувствительным психологическим данным по рабочей необходимости. Администратор платформы не становится оператором консультационного процесса, а психолог не публикует контент без проверки.

**Отброшено:** Дать `admin` полный регулярный доступ к консультациям, чатам и результатам тестов по умолчанию. Также отброшена прямая публикация материалов и тестов психологами без модерации.

### ADR-017 — Schedule v3: рабочие окна отдельно от типа встречи

**Дата:** 2026-06-27

**Статус:** реализовано 2026-07-14 (backend + admin role management + frontend
cabinet switching). Схема БД не менялась: существующая M:N `user_roles` уже
поддерживала несколько ролей.

**Контекст:** Раннее расписание смешивало доступность психолога, длительность слота и тип встречи. После появления индивидуальных и групповых форматов, буфера между встречами, ручной записи supervisor'ом и walk-in клиентов эта модель стала слишком жёсткой.

**Решение:** `schedule_rules` описывает рабочие окна психолога, а не конкретные слоты и не конкретный тип встречи. Тип встречи выбирается при поиске/создании записи через `meeting_types`; длительность и буфер берутся из `MeetingType.duration_minutes` и `MeetingType.buffer_minutes`. Повторяющиеся перерывы вынесены в `schedule_breaks`, разовые изменения остаются в `schedule_exceptions`.

**Почему:** Один и тот же рабочий интервал может обслуживать разные типы индивидуальных встреч. Слоты корректнее вычислять на лету с учётом выбранного типа, перерывов, исключений, занятых индивидуальных записей и групповых занятий.

**Связанные правила:**
- supervisor управляет расписанием сериями rules+breaks с общим `series_id`;
- редактирование серии пересоздаёт rules+breaks, но не переносит и не удаляет существующие `appointments`;
- soft-delete/restore расписания работает через `is_active` на уровне серии;
- `auto_extend` выполняется только maintenance-скриптом `scripts/extend_schedules.py`, не из FastAPI lifespan;
- ручная запись supervisor'ом создаёт `pending_confirmation`; психолог подтверждает или отклоняет её как обычную индивидуальную встречу;
- walk-in клиент хранится в `unregistered_student_cards`, а запись ссылается на `unregistered_student_card_id`;
- `group_sessions` - отдельные события, не group chat; подтверждение психолога для записи студента на группу не требуется.

**Отброшено:** Хранить готовые слоты в БД; привязывать рабочее окно к одному типу встречи; автоматически переносить существующие записи при изменении расписания; запускать автопродление расписаний внутри FastAPI startup/lifespan.

**Зафиксировано в:** `docs/HANDOFFS/2026-06-27-appointments-scheduling-complete.md`.

### ADR-018 — Multi-role user model: роли-права отдельно от активного кабинета

**Дата:** 2026-06-27

**Контекст:** Схема БД уже хранит роли через M:N (`roles` + `user_roles`), но большая часть приложения исторически работала как single-role: auth API возвращал одно поле `role`, frontend guards проверяли `user.role`, а admin edit фактически заменял одну роль другой. Новое требование: один пользователь может одновременно быть, например, `supervisor`, `psychologist` и `admin`.

**Решение:** Источник прав доступа — набор активных membership-ролей пользователя в `user_roles`. Auth/session/profile API должны возвращать `roles: Role[]`. Поле `role` можно временно сохранять как backward-compatible primary/default role для старых экранов и сортировок, но его нельзя использовать как единственный источник авторизации.

**Правила доступа:**
- backend `require_role(...)` проверяет пересечение разрешённых ролей с `current_user.roles`;
- frontend `RoleRoute` проверяет `user.roles`, а не `user.role`;
- `/dashboard` открывает выбранный активный кабинет, если он валиден для пользователя, иначе использует детерминированный default (`admin` → `supervisor` → `psychologist` → `student`) или отдельный role chooser;
- пользователь с ролями `admin` + `supervisor` попадает в `/admin/*` именно по membership-роли `admin`, а не потому что `supervisor` наследует доступ к admin panel;
- для аудита и content policy используется `effective_role`/активный кабинет, а не случайная primary role. Клиентский `active_role` допустим только как hint и всегда валидируется backend'ом по `user_roles`.

**Admin role management:** управление ролями должно быть set-based: добавить/удалить конкретные роли, не удаляя весь набор `user_roles`. Нельзя оставлять пользователя без активных ролей. Добавление staff-роли (`psychologist`, `supervisor`, `admin`) требует legal basis. Удаление staff-роли требует audit trail, но не создаёт новый legal basis. `POST /api/admin/users` принимает ровно одно из legacy `role` или `roles[]`, дедуплицирует staff-роли и атомарно пишет одну legal-basis запись на каждую уникальную создаваемую роль. Admin list/read/create responses возвращают активные `roles[]` и legacy primary `role`; отсутствие активных ролей не маскируется как `student`. Роль `student` по-прежнему не назначается через admin role control: студенты появляются через self-registration или `POST /api/supervisor/students`; если у пользователя уже есть `student`, multi-role update не должен удалять её случайно.

Для `PATCH /api/admin/users/{uuid}` отсутствие поля `roles` означает «не менять роли»,
а явный `roles: []` — целевой пустой набор staff-ролей. Такой запрос снимает все
staff-роли только если после операции остаётся другая активная роль (например,
`student`); попытка оставить пользователя без ролей отклоняется с 422. Это отличается
от create-контракта, где пустой `roles[]` всегда недопустим.

**Реализованное frontend-поведение:** все авторизованные точки входа ведут через
`/dashboard`. Для одной роли кабинет открывается сразу; для нескольких ролей
используется сохранённый валидный `activeRole`, а при его отсутствии показывается
`RoleChooser`. `CabinetSwitcher` доступен в кабинетах и профиле, меняет только
активный UI-контекст и маршрут. `RoleRoute` и backend по-прежнему независимо
проверяют membership. Явный `roles: []` не подменяется legacy `role`.

**Операционное ограничение:** добавление staff-роли через admin PATCH разрешено
только пользователю, у которого уже есть хотя бы одна активная staff-роль. Для
student-only/roleless аккаунта UI блокирует role-control, но не scalar edit; отдельный
student-to-staff promotion flow требует самостоятельного compliance-решения.

**Аккаунт без активных ролей (уточнение от 2026-08-18):** несмотря на запрет
оставлять пользователя без ролей через admin API, состояние достижимо — например,
единственная роль истекает по `user_roles.expires_at`. Контракт разделён по стадиям:

- **новый вход отклоняется** — `service.authenticate_user` fail-closed отвергает
  такой аккаунт **до** `update_last_login` и `create_session`. Отказ отдаётся как
  **HTTP 403** с audit `failed_login` / `failure_reason = no_active_roles`.
  Клиентское сообщение обобщённое: состав ролей аккаунта не раскрывается;
- **уже выданная сессия остаётся валидной** — `/api/auth/me` отдаёт `roles: []` и
  `role: null`, прикладные эндпоинты дают 403, а `logout` обязан отработать 200:
  иначе пользователь не может закрыть собственную сессию.

Ранее этот отказ возвращал **500** с `internal_error`. Это признано ошибкой:
предсказуемый доменный отказ был неотличим от настоящей аварии, шумел в мониторинге
и вводил оператора в заблуждение. `internal_error` остаётся исключительно за
настоящими внутренними сбоями; `invalid_credentials` продолжает обозначать неверные
credentials и новым кодом не подменяется. Нового audit-СОБЫТИЯ не заводится —
`no_active_roles` является исходом того же `failed_login`.

Следствие для audit-facade: user-актор с `role=None` допускается **только** для
событий `Destination.AUTH_LOG` (там роль актора не хранится вовсе). Для `AUDIT_LOG`
роль обязательна — она пишется в `audit_log.user_role`. Подставлять фиктивную роль
запрещено.

**Почему:** M:N модель уже есть в БД и лучше отражает реальную организационную структуру. Разделение membership roles и active/effective role позволяет одному человеку переключаться между кабинетами, не размывая policy каждого кабинета и не расширяя доступы через наследование ролей.

**Отброшено:**
- хранить только одну “самую сильную” роль и по ней открывать всё;
- давать `supervisor` доступ к `/admin/*` без membership-роли `admin`;
- полагаться на frontend role switcher без backend-проверки;
- менять `user_roles` через destructive replace-all при каждом PATCH пользователя.

### ADR-019 — Управляемый allowlist email-доменов для создания новых аккаунтов

**Дата:** 2026-07-16

**Статус:** реализовано.

**Контекст:** Организации нужен управляемый контроль доменов, с которых допускается
создание новых аккаунтов. Hardcoded-проверка только `gmail.com` не покрывает другие
домены, не позволяет администратору менять политику без релиза и создаёт риск
расхождения между self-registration и staff-created account flows. При этом
существующие пользователи не должны терять доступ из-за изменения политики.

**Решение:** Точные нормализованные домены хранятся в таблице
`allowed_email_domains`. Активная строка является обязательным условием для всех
HTTP/API путей создания аккаунта: self-registration, admin-created staff и
supervisor/admin-created student. Отсутствие домена в allowlist означает запрет;
отдельного denylist нет.

В registration init выполняется ранняя проверка до отправки OTP. В registration
confirm и staff-created flows authoritative проверка выполняется внутри транзакции
создания пользователя. Confirm проверяет домен до consume OTP. Creation transaction
берёт `FOR SHARE` на разрешённой строке, а изменение allowlist сериализуется
transaction-scoped advisory lock и `FOR UPDATE`; последний активный домен отключить
нельзя.

Admin управляет списком через `GET/POST/PATCH /api/admin/email-domains`. Физического
DELETE нет. Повторный POST существующего, в том числе отключённого, домена возвращает
409; реактивация выполняется явно через PATCH `is_active=true`. Изменения пишутся в
`audit_log`, но сырой comment не копируется в audit metadata.

Политика применяется только к созданию/реактивации аккаунта. Существующие
пользователи сохраняют login и password reset, даже если их домен отсутствует или
отключён. Начальный seed из 11 доменов является конфигурацией MindCare, а не
официальным или исчерпывающим государственным перечнем.

Локальный `scripts/create_admin.py` остаётся отдельным privileged bootstrap/ops
path вне allowlist. Он предназначен только для первичного развёртывания; оператор
должен вручную использовать разрешённый организацией домен. Подключение bootstrap к
той же policy требует отдельного hardening-прохода, чтобы не сломать восстановление
доступа при отсутствии первого администратора.

**Почему:** DB-backed allowlist даёт единый авторитетный контракт для всех creation
flows, управляемость без изменения кода, audit trail и безопасное конкурентное
поведение, не блокируя уже существующих пользователей.

**Отброшено:**
- hardcoded blocklist одного или нескольких иностранных доменов;
- проверка только на frontend или только в registration init;
- применение новой политики к login/password reset существующих аккаунтов;
- автоматическая реактивация отключённого домена при повторном POST;
- физическое удаление доменов и потеря истории изменений.

### ADR-020 — Администратор не может снять у себя membership-роль admin

**Дата:** 2026-07-16

**Статус:** реализовано.

**Контекст:** В multi-role admin edit пользователь мог случайно снять у собственного
аккаунта роль `admin` и немедленно потерять доступ к административному кабинету.
Frontend-предупреждения недостаточны, потому что API можно вызвать напрямую.

**Решение:** При set-based PATCH ролей backend сравнивает стабильные actor id и
target user id. Если администратор изменяет собственный аккаунт и целевой diff
удаляет активную роль `admin`, операция отклоняется с 422. Frontend блокирует только
собственный checkbox `admin` и показывает пояснение; остальные собственные
staff-роли остаются редактируемыми. Другой администратор может снять роль `admin` у
этого пользователя.

Guard относится только к удалению собственной membership-роли `admin`.
Самодеактивация и самоудаление пользователя текущим решением не запрещены и требуют
отдельного продуктового решения, если должны быть закрыты.

**Почему:** Точечный backend guard закрывает наиболее вероятную потерю доступа без
введения глобальной политики «последнего администратора» и без запрета легитимного
управления ролями другим администратором.

**Отброшено:**
- защита только disabled-checkbox на frontend;
- полный запрет изменять собственный профиль или другие собственные staff-роли;
- автоматическая выдача роли обратно после сохранения;
- неявное расширение guard на deactivate/delete без отдельного требования.

### ADR-021 — Минимизированный `data_change_log`: application-writer, name-only по умолчанию

**Дата:** 2026-08-19

**Статус:** Принято (Stage 6). Дополняет actor/target-модель `audit_log`
(см. ADR-006, помеченный SUPERSEDED).

**Контекст.** `audit_log` отвечает «кто, над чем, с каким исходом», но для
generic-PATCH операций он пишет `metadata={}`: по журналу нельзя установить,
**какие именно поля** были изменены. Это касается четырёх потоков —
`meeting_type_updated`, `group_session_updated`, `admin_user_updated`,
`unregistered_student_card_updated`. Таблица `data_change_log` существовала в
схеме с baseline, но не имела ни одного writer'а; в legacy-bootstrap SQL
(`db/sql/`) лежала функция `log_data_change(..., p_old_values jsonb,
p_new_values jsonb, ...)`, принимавшая полные ORM-строки.

**Проблема.** Наивное закрытие пробела — «писать before/after» — тиражировало бы
ФИО, телефоны, email, даты рождения, свободный текст и терапевтический контент в
третью append-only партиционированную таблицу.

**Решение.**

1. **Application-level writer, а не PostgreSQL trigger/function.**
   `record_data_change()` (`app/audit/data_change.py`) — отдельная точка входа,
   а не `Destination` в `record_event`: строка DCL не событие (нет имени
   события, outcome, metadata, description). Триггер/функция БД отвергнуты: они
   не знают прикладного разделения «generic diff vs. transition-переход», не
   могут отличить публичное поле от derived, и на уровне БД невозможно отличить
   безопасное значение от ПДн.

2. **Закрытый `CHANGE_REGISTRY`** (`app/audit/change_registry.py`): 4 таблицы,
   25 полей, 1 derived-поле. Каждая таблица объявляет `paired_event`, и при
   импорте проверяется совместимость с `REGISTRY` (destination `AUDIT_LOG`,
   совпадение `entity_type`, success-only, ATOMIC+RAISE, target REQUIRED,
   совместимость actor policy/ролей). Неизвестная таблица, операция, поле или
   тип значения — fail closed.

3. **Name-only по умолчанию.** Политика поля — `NAME_ONLY`, если явно не
   размечено иначе. 15 из 25 полей name-only; для `users` и
   `unregistered_student_cards` **все** поля name-only. Штатные Stage 6
   call sites для этих двух таблиц всегда передают values=None, поэтому
   создаваемые ими строки имеют `old_values`/`new_values IS NULL`. Это
   application-инвариант, а не DB-гарантия: исторические строки и
   привилегированный прямой SQL находятся вне него.

4. **Opt-in значений только для безопасных enum/bool/int** — 10 полей в
   `meeting_types` и `group_sessions` (конфигурация: длительность, буфер,
   порядок сортировки, флаги формата, вместимость, FK на справочник типов).
   Каждое поле несёт обязательный `justification`. Структурная гарантия:
   registry-валидация запрещает value-политику любому полю, чьё имя срабатывает
   на denylist (`is_denylisted_key`), — `full_name`, `phone`, `email`,
   `comment`, `primary_concern` физически не могут её получить.
   `psychologist_id` оставлен name-only: FK на `users` идентифицирует человека и
   под «неперсональные технические идентификаторы» не подпадает.

5. **Derived-поля исключаются.** `normalized_email` пересчитывается сервисом при
   смене email и попадает в storage-дифф, но объявлен в `derived_fields` и
   отбрасывается проекцией `project_changed_fields()`. Смена email даёт
   `changed_fields=["email"]`. Если изменилось **только** derived-поле,
   техническая мутация и generic audit сохраняются, а DCL-строка не пишется —
   пустой `changed_fields` запрещён контрактом.

6. **ATOMIC/fail-closed и общий commit с paired `audit_log`.** Writer делает
   исключительно `db.add` в caller-сессию; `commit`/`rollback`/`close`
   принадлежат владельцу бизнес-транзакции (для `users` — `update_user`, для
   остальных трёх — `appointments.service`). SOFT/fail-open режима не
   существует: нарушение контракта → `DataChangeError` до `db.add`, сбой
   хранилища → `DataChangeStorageError`; обе ошибки откатывают мутацию,
   `audit_log` и DCL вместе. Снимок `old` для value-enabled полей снимается
   **до** мутации ORM; `old == new` отвергается как детектор снимка после
   мутации.

7. **`correlation_id` не введён; парность — caller-инвариант.** Строка DCL
   пишется только рядом с успешным `paired_event` в той же транзакции, но
   facade и БД этого не проверяют. Инвариант удерживают: статические проверки
   `paired_event` при построении registry, AST-тест ровно четырёх production
   call sites и integration-тесты совместного commit/rollback. Связь
   восстанавливается по (`entity_type`/`table_name`, id, время) — это
   осознанно более слабое соединение, чем явный correlation id.

8. **Legacy `log_data_change()` удалена** миграцией `d4a7b2c9f6e1`:
   идентификация строго по OID через `to_regprocedure()` с точной сигнатурой,
   `DROP FUNCTION IF EXISTS` schema-qualified, **без `CASCADE`** (зависимость
   роняет миграцию, а не удаляет зависимые объекты). Она была единственным
   готовым SQL-путём копирования полных ORM-строк в `old_values`/`new_values`.

9. **downgrade намеренно неполный.** Снимает три CHECK и два NOT NULL (STRICT,
   без `IF EXISTS`), но функцию **не восстанавливает**: возврат небезопасного
   пути копирования ПДн не является операционной процедурой. После
   `upgrade → downgrade` legacy-БД остаётся без этой функции; её судьба —
   отдельное решение владельца такой БД.

**Природа решения.** Это **техническая мера прослеживаемости**, введённая
инженерным решением проекта. ADR не утверждает, что такой журнал прямо требуется
ФЗ-152 или иным законом, и не утверждает соответствия законодательству.

**Три уровня гарантий (разделены явно):**

| Уровень | Что гарантирует | Чего НЕ гарантирует |
|---|---|---|
| Application allowlist | В штатных writer'ах в DCL не попадают ПДн, свободный текст, ciphertext, токены | Ничего о записях в обход writer'а |
| CHECK/NOT NULL в БД | Только структурные инварианты: `record_id` присутствует и положителен, `changed_fields` присутствует и непуст, `operation` ∈ трёх значений | Не проверяет содержимое `old_values`/`new_values` и не отличает безопасное значение от ПДн |
| Удаление legacy-функции | Убирает единственный готовый SQL-путь копирования полных строк | Не запрещает написать произвольный `INSERT` заново |

**Остаточный риск (принят осознанно):** обладатель привилегий прямого SQL может
записать в `data_change_log` что угодно. Технические меры Stage 6 этот сценарий
не покрывают — он относится к контролю доступа к БД.

**Отброшено:**
- PostgreSQL trigger/функция как источник записи (см. п. 1);
- запись before/after по умолчанию для всех полей;
- `CHECK`, запрещающий непустые `old_values`/`new_values` — убил бы opt-in для
  безопасных enum/bool/int;
- `DROP COLUMN old_values, new_values` — необратимо и лишает будущей
  возможности безопасного enum-diff;
- интроспекция `db.new` для проверки парности с `audit_log` — сломалась бы от
  лишнего `flush()` между вызовами;
- дублирование transition-переходов (`is_active`, роли, `booking_enabled`,
  `status`) в DCL — они уже описаны выделенными событиями `audit_log` и
  физически отсутствуют в field-allowlist;
- подключение self-profile flow (`app/auth/*`) — вне объёма Stage 6.

**Открытые решения DPO/ответственного лица** (см. `docs/BACKLOG.md`): retention
`data_change_log`; достаточность name-only для ПДн-полей; классификация
разрешённых value-enabled полей как неперсональных; доступ привилегированных
DB-пользователей; отсутствие `correlation_id`; политика erasure для append-only
журнала; сосуществование `profile_updated.metadata.fields` и DCL как двух
механизмов для одной задачи.

Технический охват IP-анонимизации для `data_change_log` закрыт Stage 7 —
журнал включён в неё наравне с `audit_log` и `auth_log` (ADR-022);
подтверждение самого срока 90 дней остаётся за DPO.

### ADR-022 — IP-анонимизация: функция в Alembic, отделённая активация, неполный round-trip

**Дата:** 2026-08-20

**Статус:** Принято (Stage 7). Техническая мера минимизации; оценку соответствия
законодательству даёт DPO/ответственное лицо, а не эта запись.

**Контекст.** `CLAUDE.md` и `docs/COMPLIANCE.md` утверждали, что IP-адреса
анонимизируются через 90 дней функцией `anonymize_old_ips()`. Фактически на
стенде, поднятом через Alembic, этого **не происходило вообще**:

- функция жила только в legacy bootstrap-SQL (`db/sql/migrations/009_views_functions.sql`,
  `db/sql/full_schema.sql`) и в Alembic-цепочку не входила — на чистой БД её
  просто не существовало;
- ни одного вызова из кода не было;
- ни cron, ни systemd timer её не запускали;
- само legacy-тело содержало дефект: `NOW() - (days_old || ' days')::interval`
  при `days_old <= 0` даёт границу в БУДУЩЕМ и обнуляет ВСЕ `ip_address`,
  включая свежие; при `NULL` — молча ничего не делает.

**Решение.**

1. **Функция переносится в Alembic** (ревизия `c8e2b5f7a3d1`) с исправленным
   контрактом: fail-fast `days_old IS NULL OR < 1` → SQLSTATE 22023,
   `make_interval(days => days_old)` вместо конкатенации строк, единый `cutoff`
   на все три UPDATE, schema-qualified таблицы + `SET search_path`,
   `pg_try_advisory_xact_lock` (SQLSTATE 55P03) с ключом, отличным от ключа
   `ensure_audit_partitions.py`, и `bigint` вместо `integer`
   (`ROW_COUNT`/`count(*)` в PostgreSQL — bigint).

2. **`DROP` + `CREATE`, а не `CREATE OR REPLACE`.** Последний сохраняет
   ownership и ЯВНЫЕ grants: на legacy-БД, где кто-то выполнил
   `GRANT EXECUTE ... TO <role>`, такой grant пережил бы замену тела, а
   `REVOKE ... FROM PUBLIC` его бы не снял — `PUBLIC` и role-specific ACL это
   независимые записи `aclitem`. Итоговый доступ отличался бы между legacy- и
   чистой БД. Дополнительно `CREATE OR REPLACE` не может сменить тип возврата.
   `DROP` идёт **без `CASCADE`**: авторитетный enforcement — сам `RESTRICT`.

3. **Отдельная read-only `count_old_ips(integer)`** с тем же валидатором и тем
   же предикатом — чтобы dry-run был строго read-only и проверяемо совпадал с
   live-прогоном, не дублируя логику границы в Python.

4. **Установка таймера отделена от его активации.** `deploy.sh` ставит
   `mindcare-anonymize-ips.{service,timer}`, но **не включает** таймер;
   активация — только по явному `--enable-ip-anonymization` либо вручную после
   dry-run. Причина: `Persistent=true` + `enable --now` запустили бы первый
   необратимый прогон немедленно, а интерактивного подтверждения внутри
   `Type=oneshot` job быть не может. `mindcare-ensure-audit-partitions.timer`
   включается автоматически — он только создаёт партиции.

5. **Охват — ровно три audit-журнала.** `user_sessions`, `consent_records`,
   `user_legal_basis_records` не затрагиваются: там IP другого назначения
   (активная сессия, доказательство согласия, документированное основание).

6. **Round-trip намеренно неполный.** До upgrade возможны два разных состояния
   (legacy-БД с дефектным телом и Alembic-БД без функции вовсе); одна ветка
   `downgrade` не может восстановить оба. Приводим к состоянию Alembic-цепочки;
   legacy-тело не восстанавливается сознательно. `downgrade` — STRICT, без
   `IF EXISTS`: schema drift обязан ронять миграцию, а не маскироваться.

**Почему так.** Обнуление IP не создаёт риска переудержания, а снимает его,
поэтому расширение охвата на `data_change_log` безопаснее исключения. Отделение
активации — единственный способ не выполнить необратимую операцию «за
оператора»: цена ошибки асимметрична (лишний день хранения IP обратим, стёртый
IP — нет).

**Отброшено:**
- `CREATE OR REPLACE` (см. п. 2) — оставлял бы ACL в разном состоянии;
- `CASCADE` при `DROP` — молча удалил бы зависимые объекты;
- `GRANT EXECUTE` именованной роли из миграции — Stage 7 не угадывает имя роли;
- `SECURITY DEFINER` — снял бы требование табличных прав с вызывающей роли, но
  это отдельное решение с собственным threat review (hardened non-login owner,
  фиксированный `search_path`, ревизия получателей `EXECUTE`);
- запись события о прогоне в `audit_log` — потребовала бы нового helper'а в
  registry (`TargetPolicy` не имеет OPTIONAL) и роста счётчика событий;
  прослеживаемость обеспечивают maintenance-лог, journal и exit code. Это
  отдельное будущее событие, не имеющее отношения к добавленному в Stage 8
  `audit_logs_viewed` (ADR-023);
- `VACUUM`/`REINDEX` из job — решение оператора по результатам замера bloat;
- split-role deployment (migration-role ≠ maintenance-role) — объявлен
  неподдерживаемым: `SECURITY INVOKER` требует не только `EXECUTE`, но и
  `SELECT`/`UPDATE` на partitioned parent'ах, а полный least-privilege рецепт
  нельзя публиковать без проверки на живой БД.

**Ограничение.** Источник IP — `request.client.host`, поэтому за reverse-proxy
анонимизируется адрес прокси, а не конечного пользователя. Stage 7 это не
исправляет; доверенные прокси — отдельный этап (см. `docs/BACKLOG.md`).

**Открытые решения DPO/ops** (см. `docs/BACKLOG.md`): retention строк журналов;
`DROP` старых партиций; политика по `user_sessions` / `consent_records` /
`user_legal_basis_records`; подтверждение срока 90 дней; подотчётность за
модификацию audit-строк; erasure в append-only журналах; split-role deployment.

### ADR-023 — Read-only admin API журналов: закрытая проекция, redaction и аудит самого просмотра

**Дата:** 2026-08-21

**Статус:** Принято (Stage 8). Опирается на actor/target-модель `audit_log`
(ADR-021 дополняет её для `data_change_log`) и на multi-role модель ADR-018.

**Контекст.** Stages 1–7 закрыли запись трёх журналов, но не чтение:
единственным способом посмотреть, кто менял роли, кто читал заметки сессий и
какие были неудачные входы, оставался прямой SQL по базе. Построенный
audit-контур был неоперабелен, а обращение к БД мимо приложения само по себе не
оставляет следа.

**Проблема.** Наивный viewer («отдать строки как есть») означал бы выдачу
администратору сырой `metadata`, `description`, IP, User-Agent, session hash,
request URL, полных email и `old_values`/`new_values` — то есть ровно того, что
Stages 4–6 запрещали писать. Плюс исторические строки, записанные до появления
registry, не обязаны соответствовать сегодняшним контрактам.

**Решение.**

1. **Три эндпоинта, а не единая лента.** `audit_log`, `auth_log` и
   `data_change_log` имеют разные контракты и разные безопасные DTO, а
   надёжного `correlation_id` между `audit_log` и `data_change_log` не
   существует (ADR-021 §7). UNION-лента создавала бы ложное впечатление
   связности.

2. **Структурная, а не фильтрующая гарантия.** Запрещённые колонки не
   выбираются из БД и отсутствуют в Pydantic-схемах физически. «Поле есть, но
   мы его не показываем» — не принимается: такой инвариант держится на
   внимательности, а не на типах.

3. **Внутренний `users.id` не выходит наружу ни в ответе, ни в запросе.**
   Цель-человек адресуется только `target_user_uuid`; `entity_ref` и
   `record_id` для пользователя равны `null`.

   Одного запрета пар `entity_type=user`+`entity_id` и
   `table_name=users`+`record_id` для этого недостаточно. Целочисленный
   идентификатор **без указанного типа цели неоднозначен**: он сопоставляется
   в том числе с пользовательскими строками, поэтому `entity_id=<users.id>`
   возвращал бы событие над этим человеком вместе с безопасной сводкой цели —
   UUID и текущим ФИО. Перебор целых чисел давал бы отображение
   `users.id → UUID`, то есть внутренний идентификатор снова становился бы
   внешним, только через чёрный ход.

   Поэтому целочисленный идентификатор допускается **только вместе с явным
   не-пользовательским типом цели**: `entity_id` требует `entity_type`,
   `record_id` требует `table_name`. Тогда он однозначно относится к
   `meeting_types`, `appointments` и т. п. и человека не идентифицирует. Все
   четыре нарушения (отсутствие типа и пользовательский тип) отвергаются 422
   до обращения к журналам и до записи access-события, а не игнорируются молча.
   Это распространение правила проекта «внешний API использует `users.uuid`, не
   `users.id`» на фильтры, а не только на ответы.

4. **`user_id IS NULL` не равно `anonymous`.** FK всех трёх журналов объявлен
   `ON DELETE SET NULL`, поэтому после физического удаления аккаунта строки
   `login` / `logout` / `password_change` тоже теряют actor id. Класс актора
   выводится из `ActorPolicy` конкретного `EventSpec`/`TableSpec`; для
   `audit_log` и `data_change_log` дополнительно проверяется, что роль строки
   входит в `allowed_actor_roles` спеки. Строка, противоречащая собственной
   спеке, становится `unavailable` без раскрытия идентичности.

5. **Фильтр и проекция классифицируют строку одинаково по построению.**
   Множества, производные от registry, живут в единственном месте
   (`app/audit/admin_policy.py`) и импортируются и storage'ом, и сервисом.
   `unavailable` в SQL определяется как отрицание объединения трёх остальных
   предикатов — это делает разбиение тотальным и непересекающимся. Каждый
   положительный предикат оборачивается в `coalesce(expr, false)`: иначе
   трёхзначная логика (`role = 'system'` при NULL) давала бы `NULL`, а
   `NOT(NULL)` — снова `NULL`, и строка молча выпадала бы из `unavailable`.

6. **`validate_metadata()` — не финальная DTO-проекция.** Она защищает от
   мусора в БД, но пропускает всё, что объявил EventSpec, включая
   `linked_user_id` (внутренний `users.id`). Поверх неё стоит закрытый
   `_METADATA_DTO_POLICY`: `linked_user_id` → `linked_user_uuid` (батч-резолв
   одним запросом на страницу), неклассифицированный ключ отбрасывается.
   Полнота политики проверяется на импорте модуля — новый ключ в registry
   роняет старт приложения, а не утекает в ответ.

7. **Всё несогласованное редактируется, а не показывается.** Незарегистрированный
   для события код отказа, исход вне `allowed_outcomes`, target вопреки
   `TargetPolicy`, чужой `entity_type`, операция вне `allowed_operations`, поле
   вне allowlist таблицы — каждый такой случай даёт `null`/пустое значение и
   `details_redacted=true`. Для неизвестного события к `spec` не обращаются
   вовсе: его нет.

   Сюда же относится `actor.kind = unavailable`: этот класс означает «актора
   установить не удалось» и возникает только при аномалии — обнулённый
   `ON DELETE SET NULL` идентификатор, отсутствующая строка `users`, роль вне
   `allowed_actor_roles` своей спеки. Такая строка всегда несёт
   `details_redacted=true`, иначе потеря сведений выглядела бы как штатное
   «действие совершил никто». `anonymous` и `system` — полностью определённые
   классы актора и признака редактирования не получают.

8. **Просмотр журналов сам является аудируемым действием.** Новое событие
   `audit_logs_viewed` (AUDIT_LOG, `USER_REQUIRED` {admin}, target `FORBIDDEN`,
   success-only, `INDEPENDENT` + `RAISE`) пишется ПОСЛЕ выборки и ДО ответа.
   Поэтому оно физически не может попасть в собственный результат, а его сбой
   даёт 503 без единой строки журнала. metadata несёт только имя журнала и
   стабильные ИМЕНА применённых фильтров — ни дат, ни UUID, ни id, ни страниц.
   Счётчик registry: `AUTH_LOG=7`, `AUDIT_LOG=87`, всего `94`.

9. **Границы вместо «отдать всё».** Окно обязательно (по умолчанию 7 дней по
   Europe/Moscow, максимум 90), сортировка только `created_at`+`id`, `size`
   ≤ 100, глубина ≤ 100 000. Ограничение 90 дней — performance/query boundary,
   а НЕ retention policy: сроки хранения строк остаются решением DPO.

10. **Справочник фильтров вычисляется, а не хардкодится.** `/options` строится
    из живых `REGISTRY` / `CHANGE_REGISTRY`, поэтому `operations` сегодня равен
    `["UPDATE"]` (ни один `TableSpec` не допускает INSERT/DELETE), а
    `actor_kinds` для `data_change_log` — `["user","unavailable"]` без
    `system`. Обещать значение фильтра, которое заведомо даст пустую выборку,
    нельзя.

**Авторизация.** Только активная membership-роль `admin` через router-level
`require_role("admin")` + `resolve_role_or_403`. Seed-permissions `admin:audit`
и `auth:view_logs` источником доступа НЕ являются: application-level permission
enforcement в проекте отсутствует, и притворяться, что оно есть, опаснее, чем
опираться на роль.

**Индексы.** Составной PK партиционированных журналов — `(id, created_at)`
(требование PostgreSQL), поэтому хронологическая лента им не обслуживается.
Ревизия `e6c3a9f1d574` добавляет по одному индексу `(created_at, id)` на
partitioned parent каждого журнала; дочерние индексы PostgreSQL создаёт сам на
всех существующих и будущих партициях. Дополнительные индексы по `event_type` /
`table_name` / `success` не вводились: сначала замер (`EXPLAIN` на синтетическом
объёме), потом решение.

**Отброшено:**
- единая UNION-лента трёх журналов (см. п. 1);
- detail-эндпоинт и export CSV/Excel/PDF — отдельное product/security/DPO
  решение;
- свободный `ILIKE` по metadata, поиск по email/IP/User-Agent, произвольная
  колонка сортировки — каждое из них превращает журнал в инструмент
  профилирования;
- отдельное событие `audit_logs_access_denied`: generic audit отказов
  авторизации — cross-cutting дизайн, а не частный случай одного модуля;
- показ literal'а `operation` для legacy-строки вне `allowed_operations` —
  разошлось бы с фильтром, который такую операцию отвергает 422;
- `session_id`/IP/UA в ответе даже в маскированном виде;
- cursor pagination — отложена до реального роста объёма (см. `docs/BACKLOG.md`).

**Природа решения.** Это техническая мера прослеживаемости и минимизации.
ADR не утверждает, что такой viewer прямо требуется ФЗ-152 или иным законом, и
не даёт оценки соответствия законодательству — она за DPO/ответственным лицом.

**Открытые решения** (см. `docs/BACKLOG.md`): допустимость доступа ВСЕХ
admin-members к чувствительной service-use metadata; retention/архив/DROP и
erasure строк журналов; раскрытие raw IP и полного email; export; отдельная
роль compliance/supervisor для чтения журналов; cursor pagination.

### ADR-024 — Роль `student` для staff: функциональный доступ к кабинету, отклонение от role-policy

**Дата:** 2026-08-29

**Статус:** Принято (продуктовое решение владельца платформы). Опирается на
multi-role модель ADR-018. Handoff:
`docs/HANDOFFS/2026-08-29-staff-student-role-admin-nav-dark-theme.md`.

**Контекст.** Потребовалось, чтобы staff (admin/supervisor/psychologist) мог
зайти в кабинет студента (посмотреть/использовать студенческий опыт). Кабинет и
все студенческие эндпоинты закрыты `require_role("student")`, поэтому UI-хак не
работает — нужна **реальная** роль в `user_roles`.

**Проблема.** `student_profiles` в коде не создаётся нигде — студент
определяется **только по роли**. Прямая массовая выдача student staff-аккаунтам:
1. засветила бы staff в списках реальных студентов супервизора
   (`supervisor.get_students` фильтрует по `Role.name == "student"`) и в
   admin-фильтре `/admin/users?role=student`;
2. противоречит документированной role-policy (`mindcare_api/CLAUDE.md`):
   student назначается только через self-registration или staff-created student
   flow с личным согласием (`consent_records`), не через admin role control без
   отдельного compliance-решения;
3. даёт staff доступ под своим аккаунтом к студенческим функциям (дневник,
   тесты, запись на консультацию).

**Решение.**

1. **student выдаётся всем staff, но как функциональная роль без legal basis.**
   `users.storage.create_user` выдаёт student каждому новому staff в той же
   транзакции; `scripts/backfill_student_role.py` — существующим;
   `scripts/create_admin.py` — bootstrap-админам. `consent_records` и
   `user_legal_basis_records` для этой роли НЕ пишутся: это не смена основания
   обработки ПДн, а функциональный доступ к собственному кабинету.

2. **Изоляция на уровне запросов.** Реальные списки студентов исключают
   аккаунты с любой активной не-student ролью: предикат `~has_other_active_role`
   в `supervisor.get_students` и в `find_users(role='student')`. Так «student для
   staff» не смешивается с настоящими студентами.

3. **student скрыт при логине и в перечне ролей, но доступен как кабинет.**
   `selectableRoles` убирает student из выбора кабинета (RoleChooser,
   DashboardRedirect) и из бэджей `/admin/users`. `CabinetSwitcher` student
   сохраняет — это точка входа staff в кабинет студента.

**Осознанные следствия.**

- **Отклонение от прежней формулировки role-policy** зафиксировано осознанно.
  Оценка соответствия ФЗ-152 — за DPO/ответственным лицом; ADR не утверждает
  соответствия. Основание обработки студенческих данных, создаваемых самим
  staff-пользователем в его кабинете, — открытый вопрос для DPO.
- **Демотация staff:** т.к. у staff всегда есть student, `roles:[]` в
  `/admin/users` допустим (остаётся активная роль student) — админ может снять
  все служебные роли, аккаунт станет «чистым студентом». Согласуется с ADR-018
  (`roles:[]` допустим при остающейся активной роли). Дополнительную защиту
  решено **не** добавлять.
- **student по-прежнему не selectable** в admin create/edit-чекбоксах — эта
  граница сохранена; выдача идёт только автоматически (create_user/backfill/
  create_admin), не как target роли из admin UI.

**Что НЕ делалось.** Отдельный признак «staff-student» в БД (роль общая);
изоляция `_get_user_with_role(..., "student")` (точечная выборка по id, вне
списков) — остаточный риск; ретроактивная фиксация legal basis.

### ADR-025 — Impersonation администратором: вход «под именем» пользователя

**Дата:** 2026-09-01

**Статус:** Принято (продуктовое решение владельца платформы). Опирается на
session-модель (`user_sessions`) и multi-role модель ADR-018.

**Контекст.** Потребовалась кнопка «Зайти под именем» в `/admin/users`: админ
входит в кабинет пользователя (диагностика, поддержка), а в кабинете
пользователя видна ссылка возврата в профиль администратора.

**Проблема.** Impersonation-сессия иначе byte-for-byte неотличима от обычного
логина, а действия администратора в кабинете попадают в `audit_log`/
`data_change_log` под actor = целевой пользователь. Для системы под ФЗ-152 с
тремя журналами это искажает след. Возврат же требует, чтобы админская сессия
пережила impersonation, — а raw-токен админа держит только клиент.

**Решение.**

1. **Серверная отметка сессии.** Колонка `user_sessions.impersonator_user_id`
   (миграция `a1c2e3f4b5d6`, nullable FK → `users.id`, `ON DELETE SET NULL`)
   помечает impersonation-сессию. `get_current_user` (единственная точка
   «сессия → user dict») подмешивает `impersonator_user_id`/`impersonator_name`;
   `/api/auth/me` отдаёт `impersonating` + `impersonator_name` — банкер
   возврата управляется **серверной правдой**, не клиентским флагом.

2. **Эндпоинт.** `POST /api/admin/users/{uuid}/impersonate` (admin-only)
   создаёт сессию цели с `impersonator_user_id = admin` и возвращает её токен.
   Guard (`service.impersonate_target`): запрещён вход под собой (400), под
   другим admin (403), под заблокированным и под аккаунтом без активных ролей
   (403). `update_last_login` НЕ вызывается и событие `login` НЕ пишется —
   «Последний вход» цели не искажается.

3. **Возврат — client-side.** Клиент сохраняет админский токен в
   `localStorage['mindcare_impersonator']` до подмены; «Вернуться» отзывает
   impersonation-сессию (`POST /logout`), восстанавливает админский токен и
   перезагружает `/me`. Если админская сессия истекла — полный сброс с
   приглашением войти заново.

4. **Аудит акта — fail-closed.** `admin_user_impersonated` (AUDIT_LOG, actor =
   admin, target = пользователь, INDEPENDENT + **RAISE**, как `audit_logs_viewed`):
   привилегированный доступ, чья единственная гарантия — прослеживаемость, не
   должен молча пройти без записи. `session_id_hash` в context связывает строку
   с созданной сессией. При `AuditError` route отзывает уже созданную сессию
   (raw-токен клиенту не отдан → непригоден) и возвращает 503. REGISTRY 109 → 110.

**Осознанные следствия (pending для DPO).**

- **Атрибуция действий во время impersonation.** Отдельные события кабинета
  по-прежнему пишутся под actor = целевой пользователь: `session_id_hash` для
  не-auth событий не проставляется, поэтому per-action джойн на
  `impersonator_user_id` недоступен. Полностью прослеживается только сам факт
  входа (`admin_user_impersonated`). Расширение атрибуции на каждое действие —
  отдельный этап.
- **`logout` при возврате** пишется под actor = целевой пользователь (мелкая
  неточность следа); выбран ради честного отзыва impersonation-сессии.
- **Отклонение от границ BACKLOG** («no staff-access to content без отдельного
  этапа»; admin не имеет доступа к результатам тестов, Этап E): impersonation
  даёт админу функциональный доступ к кабинету пользователя. Оценка ФЗ-152 — за
  DPO; ADR соответствия не утверждает.

**Что НЕ делалось.** Короткоживущая impersonation-сессия (blast radius);
серверный revoke-эндпоинт вместо `logout`; сквозная атрибуция действий на
`impersonator_user_id`; impersonation под admin.

### ADR-026 — Вход через Яндекс ID: адаптер без client_secret и `auth_log.auth_method`

**Дата:** 2026-10-01

**Статус:** Принято (Stage Social Auth 3A, только backend). Опирается на
provider-neutral ядро Stage 2B (`app/oauth/`) и multi-role модель ADR-018.
Frontend — Stage 3B, регистрация через провайдера — Stage 4.

**Контекст.** Ядро 2B (state + PKCE + cookie binding, одноразовые state/ticket,
вход только по уже привязанной identity чистого студента) работало лишь с
тестовым FakeProvider: production-реестр был пуст, а в `auth_log` вход через
провайдера был неотличим от входа по паролю. Сверено с официальной
документацией Яндекс ID 2026-10-01 и вручную с консолью Яндекс OAuth
(DEV-приложение `MindCare (DEV)`: Redirect URI
`http://localhost:8000/api/auth/oauth/yandex/callback` принят; без прав
приложение не создаётся — выбрано «Адрес электронной почты»).

**Решение.**

1. **Только адаптер.** `app/oauth/providers/yandex.py` реализует существующий
   `OAuthProvider`; контракт (`ProviderCallback`/`ProviderIdentity`) и
   конвейер callback не меняются, Яндекс-веток в service/routes нет. Адреса
   `oauth.yandex.ru/authorize`, `/token`, `login.yandex.ru/info` — константы
   модуля, не настройки.
2. **PKCE S256 без client_secret.** Документация Яндекса: при переданном
   `code_verifier` секрет не требуется. Код может прийти только на
   зарегистрированный Redirect URI, verifier есть только у backend — секрет
   почти ничего не добавляет, но требует хранения и ротации. Запрос токена —
   форма `grant_type`/`code`/`code_verifier`/`client_id`; `redirect_uri`
   Яндекс для него не документирует. Если живой Яндекс вернёт
   `invalid_client`, это отдельное решение, а не молчаливое добавление секрета.
3. **Субъект — `id`, не `psuid`.** `psuid` строится из пары client_id +
   пользователь: разный у DEV/PROD-приложений и меняется при перерегистрации
   приложения (ClientID изменить нельзя). `id` хранится строкой как есть
   (str, 1..255, без управляющих символов); формат «только цифры» не
   требуется — документация его не гарантирует. `client_id` в user-info обязан
   совпасть с настроенным (защита от подмены токена).
4. **Минимизация.** `scope=login:email` (минимальное право, без которого
   приложение не создаётся), но email и имя не читаются:
   `ProviderIdentity.email/suggested_name = None`. Токены провайдера живут
   только внутри вызова адаптера, не сохраняются и не логируются; токен
   user-info — только в заголовке `Authorization: OAuth`.
5. **HTTP.** Sync `httpx.Client` (runtime-зависимость), таймауты 3/5/5/3 с,
   без редиректов и повторов, ответ ≤ 64 KiB. Сеть/5xx/429/3xx/битый ответ →
   `ProviderUnavailable`, отказ Яндекса (4xx, нет токена/`id`, чужой
   `client_id`) → `ProviderRejected`; наружу ядро по-прежнему отдаёт
   `oauth_failed`. Исключения httpx несут заголовки запроса — адаптер их не
   логирует и поднимает новую ошибку без цепочки.
6. **Включение из конфигурации.** `YANDEX_OAUTH_ENABLED` +
   `YANDEX_OAUTH_CLIENT_ID`; `bootstrap.register_configured_providers()` в
   lifespan регистрирует адаптер только при валидной конфигурации и адресах
   `https://` или `http://` на loopback. Неполная конфигурация не роняет
   MindCare — провайдер просто недоступен (404). Проверка не опирается на
   `ENV`.
7. **`auth_log.auth_method`** (migration `b8d2f6a3c9e4`): `VARCHAR(20) NULL` +
   CHECK (`password`/`yandex`/`vk`), без индекса. Facade принимает только
   `AuthMethod` enum; политика события — `login` REQUIRED, `failed_login`
   OPTIONAL, остальные AUTH_LOG — FORBIDDEN. OAuth-провайдер берётся из
   сервиса (имя зарегистрированного адаптера / провайдер списанного ticket),
   не из сырого path; невалидный ticket → NULL. `mfa_method` не
   переиспользуется (другой смысл).
8. **Backfill без догадок.** До 3A реального провайдера в production не было:
   `login` → `password`; `failed_login` → `password` только при заполненном
   `user_email` (парольный вход и legacy-хелпер всегда его писали, OAuth-ветка
   2B — нет) и не-OAuth коде; неоднозначные строки и прочие события — NULL.
   Downgrade fail-closed при строках `yandex`/`vk`.

**Осознанные следствия.**

- Полный вход Яндекс → сессия MindCare возможен только для заранее
  привязанной identity; привязки и регистрации пока нет. Живая проверка
  неизвестного пользователя заканчивается `social_registration_not_available`
  — это корректный результат 3A.
- Не подтверждено документацией Яндекса: код ошибки при отмене
  (`access_denied`), возврат `state` в callback-ошибке, приём запроса токена
  без секрета на практике. Отмена с другим кодом покажется пользователю как
  `oauth_failed` (fail-safe).
- Production требует отдельного приложения, HTTPS, маскировки query callback
  на reverse proxy, trusted proxy и верификации сервиса — см.
  `deploy/README.md`.

**Что НЕ делалось.** Frontend, регистрация/привязка, VK, хранение токенов
провайдера, client_secret, production-приложение и reverse proxy.

### ADR-027 — Регистрация через Яндекс ID: единая кнопка, профиль Яндекса, OTP MindCare

**Дата:** 2026-10-02 (пересмотрено 2026-10-05 — UX hotfix Stage 4)

**Статус:** Принято (Stage Social Auth 4). Продолжает ADR-026; опирается на
фундамент 2A (`oauth_pending_tickets.kind='registration'`,
`users.password_hash` NULL) и multi-role модель ADR-018. Миграции нет.

**Контекст.** После Stage 3B войти через Яндекс мог только пользователь с
заранее привязанной identity, а привязать её было нечем: новый человек получал
«аккаунт пока не привязан». Нужен законченный сценарий без ручной «привязки».

**Пересмотр (UX hotfix).** Первая редакция Stage 4 просила пользователя после
Яндекса ввести имя и email MindCare вручную, затем код. Это лишний экран и
повторный ввод данных, которые Яндекс уже знает. Было: Яндекс → форма «имя +
email + согласие» → OTP. Стало: Яндекс → email и имя из профиля Яндекса → OTP
MindCare на этот email (с компактным согласием на том же шаге) → аккаунт и
сессия.

**Решение.**

1. **Одна кнопка — один поток.** «Яндекс» на вкладках «Вход» и «Регистрация»
   запускает один и тот же OAuth-поток, вкладка намерение не передаёт. После
   callback backend решает сам: identity `(provider, subject)` известна — вход,
   неизвестна — регистрация. Новый пользователь может нажать кнопку на «Входе»,
   существующий — на «Регистрации».
2. **Права и минимум данных.** Запрашиваются `login:email login:info`. Из
   профиля читаются только `id` (subject), `default_email` и имя (`first_name`
   + `last_name` → `real_name` → `display_name` → `login`). Пол, телефон, дата
   рождения, аватар, `psuid` и токены провайдера не читаются и не сохраняются.
   Нет пригодного email у новой identity — отказ `oauth_email_required` без
   ticket (fail closed); вход по уже привязанной identity от email не зависит.
3. **Ticket регистрации.** Для неизвестной identity callback создаёт
   одноразовый ticket (`kind='registration'`, в БД только SHA-256, TTL 30 минут,
   повторная отправка кода срок не продлевает) сразу с нормализованным email и
   именем провайдера. Клиент их не передаёт и изменить не может: init
   принимает только `{ticket}`. На callback не создаётся ни пользователь, ни
   identity, ни сессия, и `failed_login` не пишется.
4. **Два независимых фактора.** Яндекс подтверждает внешний subject и сообщает
   адрес; владение адресом подтверждает OTP MindCare, отправленный на этот
   email. Согласие Яндекса не заменяет согласий MindCare: confirm требует явного
   `consent_accepted=true` (чекбокс на шаге кода, отдельного экрана нет) и пишет
   те же обязательные `consent_records`, что обычная регистрация. Без согласия
   ничего не создаётся и код не проверяется.
5. **Allowlist доменов к регистрации через Яндекс не применяется** (намеренно).
   Политика ADR-019 ограничивает адреса, которые человек вводит вручную; здесь
   адрес выдаёт Яндекс ID и затем подтверждает OTP. Исключение узкое: только
   init/confirm регистрации через провайдера. Регистрация по email и паролю,
   admin-created staff и supervisor-created student по-прежнему проверяют
   allowlist; таблица доменов и её API не менялись (регрессия покрыта тестом).
6. **Никакого auto-link.** Email провайдера, уже принадлежащий аккаунту
   (активному или soft-deleted), — одинаковый отказ «Аккаунт с таким email уже
   существует. Войдите по email и паролю.» без привязки и без реактивации;
   ticket при этом сжигается (его email неизменен). Связать провайдера с
   существующим аккаунтом можно будет только аутентифицированным действием из
   настроек (Stage 5).
7. **Имя — начальное значение профиля.** `users.full_name` берётся из имени
   Яндекса (без него — локальная часть email). Это не подтверждённое ФИО;
   пользователь меняет его в существующем профиле.
8. **Аккаунт без пароля.** `password_hash = NULL`, без сгенерированного пароля
   и заглушек; первый пароль ставится существующим сбросом по email.
9. **Атомарность.** Init — проверки ticket и выпуск OTP одним commit, письмо
   после commit. Confirm — одна транзакция: пользователь, роль student,
   согласия, identity, погашение OTP и ticket, сессия, `last_login`.
   Сериализация — блокировки строк ticket и OTP, последняя линия — UNIQUE.
   Неверный код не сжигает ticket; identity/email «уже существуют» — сжигают;
   технический сбой откатывает всё и не маскируется под «неверный код».
10. **OTP без миграции.** Используется общая `otp_verifications`
    (`password_hash NULL`). Потоки разведены условиями: social confirm требует
    живой ticket, NULL-хеш и отсутствие пользователя с этим email; обычная
    регистрация по-прежнему отклоняет NULL-хеш; сброс пароля требует
    существующего пользователя.
11. **UI.** Шаг кода — общий компонент `RegistrationOtpStep` для регистрации по
    паролю и через Яндекс; вкладок «Вход | Регистрация» на нём нет. После
    callback код отправляется автоматически ровно один раз (в том числе в
    React StrictMode), email показывается маскированным.
12. **Аудит.** `registration_succeeded` и `login` с `auth_method=yandex`; отказы
    confirm — `registration_failed`. Регистрация по паролю оставляет
    `auth_method` NULL (история не переписывается).

**Осознанные следствия.**

- Пользователь, чей email уже зарегистрирован, войти через Яндекс не может до
  Stage 5.
- Регистрироваться через Яндекс можно с любым адресом Яндекса, в том числе с
  доменом вне allowlist (п. 5). Если организации нужно ограничение круга лиц,
  его придётся вводить отдельно (например, привязкой к учётной записи вуза) —
  оценка за DPO/владельцем продукта.
- Сменить email, выданный Яндексом, в регистрации нельзя: другой адрес — через
  обычную регистрацию.
- Связь OTP с ticket логическая, отдельной колонки и счётчика попыток на ticket
  нет; их заменяют лимит попыток OTP, cooldown, rate limit (по SHA-256 digest
  ticket для init и confirm) и срок жизни ticket.
- Ticket живёт только в памяти приложения: перезагрузка страницы требует
  начать заново. (С UX hotfix VK-1B шаг кода показывает AuthModal на главной,
  а `/auth/callback` — технический маршрут; см. ADR-028 п. 8.)

**Что НЕ делалось.** Привязка к существующему аккаунту, VK (кнопка видна, но
отключена), Telegram, синхронизация профиля провайдера при последующих входах,
новые виды согласий, миграции.

### ADR-028 — Регистрация через VK ID: выбор email, allowlist, OTP MindCare

**Дата:** 2026-10-06

**Статус:** Принято (Stage Social Auth VK-1A/VK-1B). Продолжает ADR-026/027.
Миграции нет.

**Контекст.** VK ID подключён к тому же provider-neutral OAuth-ядру, что и
Яндекс (OAuth 2.1 Authorization Code + PKCE, публичный клиент без ключей,
`device_id` только на время обмена кода). Живая проверка на DEV-приложении
показала: VK возвращает стабильный `user_id` и имя, но email может **не
вернуть**, даже когда в кабинете приложения почта отмечена обязательной.
Регистрация «как у Яндекса» (email профиля фиксирован, код уходит сам) для VK
невозможна.

**Решение.**

1. **Свой шаг email.** Для новой VK identity callback создаёт ticket
   регистрации (адрес VK, если он есть, — лишь предложение; его может не быть)
   и ведёт на шаг email: адрес VK показывается маскированным и только для
   чтения с действием «Нет доступа к этой почте? Указать другую»; если адреса
   нет — сразу поле ввода. Шаг живёт внутри существующей AuthModal на главной
   (п. 8); отдельной страницы или модалки регистрации через VK нет.
2. **Любой адрес подтверждается кодом MindCare.** Неважно, пришёл адрес от VK
   или введён вручную: до создания аккаунта он проходит нормализацию, allowlist
   доменов, проверку занятости и OTP MindCare.
3. **Allowlist обязателен.** К VK применяется тот же allowlist доменов, что у
   регистрации по email и паролю: на init и повторно внутри транзакции
   confirm. Адрес VK вне allowlist использовать нельзя — пользователь указывает
   адрес разрешённого домена.
4. **Email — только из ticket.** Выбранный адрес записывается в ticket под
   блокировкой в той же транзакции, что выпуск кода. Confirm email от клиента
   не принимает. Адрес можно сменить до успешного confirm новым init: на новый
   адрес уходит новый код, код прежнего адреса регистрацию не подтверждает.
5. **Никакого auto-link.** Занятый email (в том числе у soft-deleted аккаунта)
   — отказ на шаге email без привязки и без восстановления; ticket при этом не
   сжигается, пользователь указывает другой адрес. `users.email` остаётся
   обязательным, social-аккаунтов без email нет. Один `(vk, user_id)` — максимум
   один пользователь; один email — максимум один пользователь.
6. **Один provider.** Вход через Mail.ru или QR внутри VK ID возвращает обычную
   VK identity и обрабатывается тем же потоком `vk`; отдельных провайдеров и
   логики для них нет.
7. **Политика провайдеров — в одном месте.** Отличия Яндекса и VK сведены к
   двум признакам в `app/oauth/policy.py` (`email_choice`,
   `enforce_allowlist`); ядро веток по имени провайдера не содержит.
8. **Контейнер — главная + AuthModal (UX hotfix).** `/auth/callback` —
   технический маршрут без своих форм и карточки: ticket регистрации он
   передаёт в память приложения (`AuthContext.socialRegistration`, React state)
   и делает replace на `/`, где шаг email и шаг кода показывает та же
   AuthModal в режимах `socialEmail` / `socialOtp` (вкладок «Вход |
   Регистрация» в них нет). Ticket не переносится через URL, router state,
   `localStorage` и `sessionStorage`; обновление страницы его теряет — это
   безопасное и ожидаемое поведение, пользователь начинает вход через
   провайдера заново. «Начать заново», закрытие модалки, терминальная ошибка,
   появление сессии и уход с главной ticket из памяти убирают. То же
   относится к шагу кода регистрации через Яндекс: продуктовое поведение
   прежнее, изменился только контейнер. Backend-контракты не менялись.

**Осознанная асимметрия.** Регистрация через Яндекс allowlist не проверяет
(ADR-027 п. 5), через VK и по паролю — проверяет. Это продуктовое решение, а
**не** инвариант безопасности системы: allowlist сейчас не ограничивает круг
лиц, потому что обойти его можно регистрацией через Яндекс. Если организации
нужно реальное ограничение, политику Яндекса придётся менять отдельным
решением (оценка — DPO/владелец продукта). В рамках VK-1B Яндекс не менялся.

**Следствия.**

- Код может быть отправлен на любой адрес разрешённого домена, который указал
  пользователь VK, — как и при обычной регистрации; ограничения — лимиты по
  ticket, IP и самому адресу, cooldown 60 с.
- Имя берётся из VK (не подтверждённое ФИО); без него — локальная часть
  итогового адреса. Отдельной формы ФИО нет.
- Связь OTP с ticket по-прежнему логическая (по email); смена адреса не
  удаляет код прежнего адреса — он просто перестаёт что-либо подтверждать.

**Что НЕ делалось.** Отдельные провайдеры Mail.ru/Одноклассники, привязка и
отвязка VK в настройках, объединение аккаунтов, nullable email, Telegram,
изменение потока и политики Яндекса, миграции.
